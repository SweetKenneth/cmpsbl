## CONTEXT

You are restoring a CMPSBL cognitive operating system from a disaster recovery archive. Full restoration requires **two artifacts**:

1. **Source code** — obtained from Lovable (Dashboard → Settings → Download ZIP) or GitHub

## RESTORE SEQUENCE

Execute these steps **in exact order**. Do not skip or reorder.

### STEP 1 — Extract Source Code

```bash
unzip cmpsbl-source.zip -d restored-project
cd restored-project
```

**Verify:** Confirm `package.json`, `src/`, `supabase/migrations/`, and `supabase/functions/` exist.

### STEP 2 — Extract Backup Data

```bash
unzip cmpsbl-full-backup-*.zip -d backup-data
```

**Verify:** Confirm `backup-data/data/`, `backup-data/schema/`, and `backup-data/manifest.json` exist. Note that data is stored as `data/<table_name>/part-NNNNN.json` (paginated chunks, up to 1000 rows per file).

### STEP 3 — Install Dependencies

```bash
npm install
# or: bun install
```

**Verify:** `node_modules/` directory created without errors.

### STEP 4 — Configure Environment

Create `.env` in the project root:

```env
VITE_SUPABASE_URL=https://<PROJECT_REF>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=<ANON_KEY>
VITE_SUPABASE_PROJECT_ID=<PROJECT_REF>
```

**Critical:** These three variables are required. The app will not start without them.

### STEP 5 — Link Supabase Project & Apply Schema

```bash
supabase link --project-ref <PROJECT_REF>
supabase db push
```

This applies all migrations from `supabase/migrations/` in chronological order.

**If migration fails:**
1. Identify the failing migration file from the error output
2. Run migrations individually: `supabase migration up --include <filename>`
3. Common cause: table or type already exists → safe to skip that migration
4. Fix any conflicts before proceeding

**Verify:** All migrations applied. Run `supabase db diff` — output should be empty.

### STEP 6 — Import Table Data

The backup's auto-generated `RESTORE.md` (inside the backup ZIP) contains a ready-to-run `restore-data.mjs` script tailored to your exact backup. **Use that script.**

If you need to write your own, here is the pattern:

```javascript
// restore-data.mjs
import { createClient } from '@supabase/supabase-js';
import fs from 'fs';
import path from 'path';

const SUPABASE_URL = '<YOUR_PROJECT_URL>';
const SERVICE_ROLE_KEY = '<YOUR_SERVICE_ROLE_KEY>';
const supabase = createClient(SUPABASE_URL, SERVICE_ROLE_KEY);
const dataDir = './backup-data/data';

const tableDirs = fs.readdirSync(dataDir)
  .filter(name => fs.statSync(path.join(dataDir, name)).isDirectory())
  .sort();

for (const table of tableDirs) {
  const tableDir = path.join(dataDir, table);
  const partFiles = fs.readdirSync(tableDir)
    .filter(f => f.startsWith('part-') && f.endsWith('.json'))
    .sort();

  if (partFiles.length === 0) {
    console.log(`⏭️  ${table}: no data parts`);
    continue;
  }

  let imported = 0;
  let failed = 0;

  for (const partFile of partFiles) {
    const rows = JSON.parse(fs.readFileSync(path.join(tableDir, partFile), 'utf-8'));
    if (!Array.isArray(rows) || rows.length === 0) continue;

    const { error } = await supabase
      .from(table)
      .upsert(rows, { onConflict: 'id', ignoreDuplicates: false });

    if (error) {
      // Some tables use composite keys — try insert instead
      const { error: insertError } = await supabase.from(table).insert(rows);
      if (insertError) {
        console.error(`  ❌ ${table} ${partFile}: ${insertError.message}`);
        failed += rows.length;
      } else {
        imported += rows.length;
      }
    } else {
      imported += rows.length;
    }
  }

  console.log(`✅ ${table}: ${imported} imported${failed ? `, ${failed} failed` : ''}`);
}

console.log('\n🎉 Data import complete!');
```

**Critical notes:**
- Use the **service role key** (not the anon key) to bypass RLS during import
- Data is in `data/<table_name>/part-NNNNN.json` subdirectories, NOT flat files
- The script tries `upsert` with `onConflict: 'id'` first, then falls back to `insert` for tables with composite primary keys
- Tables are imported alphabetically — most foreign key constraints are deferred or handled by upsert; if a specific table fails, re-run it after its dependency is imported

### STEP 7 — Create Admin User

Auth users are **not** included in the backup. You must create a new user:

1. Start the app (`npm run dev`) and sign up via the UI
2. Then grant admin access:

```sql
-- Run in Supabase SQL Editor:
INSERT INTO public.user_roles (user_id, role)
VALUES ('<YOUR_NEW_USER_ID>', 'admin');
```

Find your user ID in the Supabase Auth dashboard or by querying `auth.users`.

## ERROR RECOVERY

| Symptom | Diagnosis | Fix |
|---------|-----------|-----|
| `relation does not exist` | Migrations not fully applied | Re-run `supabase db push` |
| `violates foreign key constraint` | Table dependency ordering | Import the referenced table first, then retry |
| `column "id" does not exist` or `onConflict` error | Table uses composite PK | Use `insert` instead of `upsert` for that table |
| `JWT expired` or `invalid token` | Wrong anon key in .env | Check credentials from Supabase dashboard |
| `function not found` | Edge functions not deployed | Run `supabase functions deploy` |
| `VITE_SUPABASE_URL is undefined` | Missing .env file | Create .env per Step 4 |
| `permission denied` | RLS blocking import | Confirm you're using service_role key, not anon key |
| Build fails with missing module | Incomplete install | Delete `node_modules`, reinstall |
| Can't access /os dashboard | Missing admin role | Run the SQL from Step 7 |

## ARCHITECTURE NOTES FOR AI AGENTS

This system is a **cognitive operating system**, not a standard web app. Key concepts:

- **40 nodes** form the substrate (BRAIN, MEMORY, DEFENSE, CORTEX, etc.)
- **Resolvers** are the execution surface: `node.resolver_name`
- **Intent routing** via `broadcastIntent()` coordinates all actions
- **Mesh communications** power real-time telemetry dashboards
- **Memory Stream** is the discovery engine generating new software pipelines

Do not restructure the architecture. Preserve node ownership, resolver naming, and intent routing patterns.

## SKIPPED TABLES REFERENCE

The backup intentionally skips high-volume telemetry and event tables that are regenerated at runtime. These include:

- `brain_events`, `mesh_comms`, `analytics_events` (telemetry)
- `intent_receipts`, `resolver_execution_log` (execution logs)
- `access_usage`, `access_quotas` (metering)
- `owner_reports` (generated reports)
- Any table matching patterns: `*_events`, `*_logs`, `*_traces`, `*_telemetry`, `*_snapshots`, `*_receipts`, `*_audit*`, `*_metrics*`, `*_queue`, `*_usage`, `*_quotas`

These tables will be empty after restore and will repopulate as the system runs.
