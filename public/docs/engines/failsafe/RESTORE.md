# RESTORE.md — AI-Agent Restore Protocol
## FAILSAFE Disaster Recovery Engine · Machine-Readable Instructions

**Format:** Structured restore protocol for autonomous AI agents  
**Version:** 3.0.0  
**Compatibility:** Any Supabase-backed web application  

---

## CONTEXT

You are restoring a web application from a FAILSAFE disaster recovery archive. Full restoration requires **two artifacts**:

1. **Source code** — the application's codebase (from Git, Lovable, or another source)
2. **Backup ZIP** — the database backup generated by FAILSAFE

The backup ZIP contains database table data (paginated JSON), schema metadata, and storage bucket listings. It does **not** contain source code, auth users, storage file contents, or secrets.

## RESTORE SEQUENCE

Execute these steps **in exact order**. Do not skip or reorder.

### STEP 1 — Set Up Source Code

Get your application source code and install dependencies:

```bash
# Clone from Git or extract from ZIP
cd your-project
npm install
```

**Verify:** `package.json` and `node_modules/` exist.

### STEP 2 — Extract Backup Data

```bash
unzip backup-*.zip -d backup-data
```

**Verify:** `backup-data/data/`, `backup-data/schema/`, and `backup-data/manifest.json` exist.

**Data format:** Table data is stored as `data/<table_name>/part-NNNNN.json` — each part contains up to 1000 rows as a JSON array.

### STEP 3 — Configure Environment

Create or update `.env` in the project root with your new Supabase credentials:

```env
VITE_SUPABASE_URL=https://<PROJECT_REF>.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=<ANON_KEY>
VITE_SUPABASE_PROJECT_ID=<PROJECT_REF>
```

Adjust variable names if your project uses different env var naming conventions.

### STEP 4 — Apply Database Schema

```bash
npx supabase link --project-ref <PROJECT_REF>
npx supabase db push
```

This applies all migrations from `supabase/migrations/` in chronological order.

**If migration fails:**
1. Check the error output for the specific failing migration
2. Run individually: `npx supabase migration up --include <filename>`
3. Common cause: object already exists → safe to skip
4. Resolve conflicts before proceeding

**Verify:** `npx supabase db diff` returns empty output.

### STEP 5 — Import Table Data

The backup's auto-generated `RESTORE.md` (inside the ZIP) contains a ready-to-run import script tailored to your exact data. **Use that script if available.**

Otherwise, create `restore-data.mjs`:

```javascript
import { createClient } from '@supabase/supabase-js';
import fs from 'fs';
import path from 'path';

const SUPABASE_URL = '<YOUR_PROJECT_URL>';
const SERVICE_ROLE_KEY = '<YOUR_SERVICE_ROLE_KEY>';
const supabase = createClient(SUPABASE_URL, SERVICE_ROLE_KEY);
const dataDir = './backup-data/data';

const tableDirs = fs.readdirSync(dataDir)
  .filter(name => fs.statSync(path.join(dataDir, name)).isDirectory())
  .sort();

for (const table of tableDirs) {
  const tableDir = path.join(dataDir, table);
  const partFiles = fs.readdirSync(tableDir)
    .filter(f => f.startsWith('part-') && f.endsWith('.json'))
    .sort();

  if (partFiles.length === 0) continue;

  let imported = 0;
  let failed = 0;

  for (const partFile of partFiles) {
    const rows = JSON.parse(fs.readFileSync(path.join(tableDir, partFile), 'utf-8'));
    if (!Array.isArray(rows) || rows.length === 0) continue;

    // Try upsert first (works for tables with 'id' primary key)
    const { error } = await supabase
      .from(table)
      .upsert(rows, { onConflict: 'id', ignoreDuplicates: false });

    if (error) {
      // Fallback to insert for tables with composite or non-'id' primary keys
      const { error: insertError } = await supabase.from(table).insert(rows);
      if (insertError) {
        console.error(`  ❌ ${table} ${partFile}: ${insertError.message}`);
        failed += rows.length;
      } else {
        imported += rows.length;
      }
    } else {
      imported += rows.length;
    }
  }

  console.log(`✅ ${table}: ${imported} imported${failed ? `, ${failed} failed` : ''}`);
}

console.log('\n🎉 Data import complete!');
```

Run it:

```bash
node restore-data.mjs
```

**Critical notes:**
- Use the **service role key** (not anon key) to bypass RLS during import
- If a table fails with a foreign key error, note it and re-run after its dependency table is imported
- The script handles both `id`-based and composite primary keys via the upsert→insert fallback

### STEP 6 — Recreate Storage Buckets (If Applicable)

If your backup includes `storage/buckets.json`, recreate the buckets:

```sql
-- Run in Supabase SQL Editor for each bucket:
INSERT INTO storage.buckets (id, name, public)
VALUES ('bucket-name', 'bucket-name', true)
ON CONFLICT (id) DO NOTHING;
```

Then re-upload your storage files from your separate backup of those assets.

### STEP 7 — Deploy Edge Functions (If Applicable)

If your project uses Supabase Edge Functions:

```bash
npx supabase functions deploy --project-ref <PROJECT_REF>
```

Reconfigure any required secrets:

```bash
npx supabase secrets set SECRET_NAME=secret_value
```

### STEP 8 — Set Up Users & Permissions

Auth users are **not** included in backups (Supabase auth tables cannot be exported). Users must re-register.

If your app uses a roles table, you'll need to manually assign roles after creating new users:

```sql
-- Example: grant admin role after signing up
INSERT INTO public.user_roles (user_id, role)
VALUES ('<user-id>', 'admin');
```

### STEP 9 — Build & Verify

```bash
npm run build
npm run dev
```

**Verify:**
1. Application loads without errors
2. Authentication flow works
3. Database data is accessible
4. Edge functions respond (if applicable)

## ERROR RECOVERY

| Symptom | Diagnosis | Fix |
|---------|-----------|-----|
| `relation does not exist` | Schema not applied | Run `npx supabase db push` |
| `violates foreign key constraint` | Import order issue | Import the referenced table first, retry |
| `onConflict` or `column "id" not found` | Composite primary key | Script auto-falls back to `insert` |
| `JWT expired` / `invalid token` | Wrong key in .env | Check credentials from Supabase dashboard |
| `permission denied` | RLS blocking import | Confirm you're using service_role key |
| Missing env vars | .env not configured | Create .env per Step 3 |
| Build fails | Dependencies missing | Delete `node_modules` and reinstall |

## UNDERSTANDING THE BACKUP FORMAT

### manifest.json

Contains metadata about the backup:
- `created_at` — when the backup was taken
- `tables` — row counts per table (`-1` = failed, `--2` = skipped due to timeout, `-3` = intentionally skipped)
- `table_parts` — number of part files per table
- `total_rows` — total rows exported
- `timed_out` — whether the backup hit the time limit
- `errors` — count of errors during export

### Data Files

Each table's data is split into `part-NNNNN.json` files containing up to 1000 rows each. This chunking prevents memory issues with large tables. To get all rows for a table, read and concatenate all part files in order.

### Skipped Tables

Some tables may be intentionally skipped (marked `-3` in manifest). These are typically:
- High-volume event/telemetry tables
- Log tables
- Cache tables
- Anything that regenerates from runtime activity

Check `manifest.json` → `tables` to see exactly which tables were exported vs skipped.
