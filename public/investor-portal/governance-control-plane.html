Governance Control Plane

Operational Mode Management · Audit Architecture · Safety Rails

Why Governance-First

Most AI systems treat governance as an afterthought — a monitoring dashboard bolted on after deployment. CMPSBL inverts this. Governance is an architectural layer that wraps the entire substrate. No operation executes without passing through the governance surface.

This is not a philosophical position. It is an engineering constraint. The GOVERNANCE overlay is the innermost mesh — the last gate before any mutation reaches the substrate. The system cannot bypass it.

Governance is not a feature. It is the innermost constraint surface of the runtime.

Operational Modes

The control plane supports four distinct operational modes. The system defaults to ACTIVE and can only be changed by authenticated system administrators with explicit reason logging.

ACTIVE

Standard operation. All subsystems running — continuous learning, dream consolidation, and evolution scanning are active. This is the default state and the state the system returns to after any time-bounded mode change expires.

OBSERVE

Quiet mode. All mutation pipelines are paused — continuous learning, dream processing, and evolution proposals stop. Read-only telemetry and basic health probes continue. Useful for controlled observation periods or pre-deployment assessment windows.

LOCKDOWN

Incident response mode. Non-essential background processes are halted. Aggressive rate limiting is applied. Only core services remain active: authentication, state continuity, the core API surface, audit logging, and basic health reporting. Designed for active incident management.

EVOLVE

Directed acceleration. All learning systems are active with additional safeguards: governance scoring thresholds are enforced, canary rollouts are required for all promotions, and automatic rollback is enabled for low-confidence changes. Used during controlled improvement windows.

TTL Auto-Revert

Any non-ACTIVE mode can be assigned a time-to-live (TTL) in minutes. When the TTL expires, the system automatically reverts to ACTIVE mode. This prevents accidental lock-in to degraded operational states.

The auto-revert is itself an audited event. If an administrator sets LOCKDOWN with a 60-minute TTL, the system will:

  • Enter LOCKDOWN immediately
  • Log the mode change with administrator identity, reason, and TTL
  • After 60 minutes, automatically revert to ACTIVE
  • Log the auto-revert as a distinct audit event

Additionally, a one-click "panic revert" is available to immediately return to ACTIVE from any state, bypassing the TTL countdown.

Audit Logging

Every mode transition is recorded in an append-only audit log with the following fields:

FieldDescription
Previous ModeThe mode the system was in before the change
New ModeThe mode being transitioned to
Changed ByAuthenticated administrator identity
ReasonFree-text rationale (required)
TTLAuto-revert duration, if set
TimestampISO 8601 with millisecond precision
Affected SubsystemsSummary of subsystem state changes

The audit log is immutable. Entries cannot be modified or deleted after creation.

Safety Rails

  • Default-safe — The system defaults to ACTIVE. If governance state cannot be read, the system assumes ACTIVE.
  • TTL-bounded — Non-ACTIVE modes must specify a TTL or be manually reverted. The system cannot be accidentally left in a degraded state.
  • Admin-only access — Mode changes require authenticated owner/admin role. No tenant administrator or end-user can access the governance surface.
  • Reason-required — Every mode change requires a written rationale. No silent transitions.
  • Panic revert — One-click immediate return to ACTIVE from any state.
  • No self-modification — The governance layer cannot modify its own constraints. Governance rules are kernel-enforced.

Implications for Investors

The governance control plane provides three properties that institutional evaluators typically look for:

  • Auditability — Complete, immutable record of all operational state changes with attribution.
  • Containment — The system cannot escalate its own permissions or modify governance constraints.
  • Recoverability — Any state can be reverted to baseline operation instantly, with full audit trail.
