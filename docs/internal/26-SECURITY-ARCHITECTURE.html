Security Architecture

Classification: Internal — Confidential
Epoch: SPARTA (v11.1)
Last Updated: February 2026

1. Security Model Overview

The CMPSBL substrate implements a defense-in-depth security model with five concentric protection layers:

Layer 1: DEFENSE overlay (perimeter)
  └── Threat detection, rate limiting, IP reputation
Layer 2: Input validation (hardening primitives)
  └── String/numeric/collection bounds at every entry point
Layer 3: GOVERNANCE overlay (policy)
  └── Ethical constraints, consent management, audit
Layer 4: RLS policies (data access)
  └── Row-Level Security on all database tables
Layer 5: Circuit breaker isolation (fault containment)
  └── Per-node failure isolation prevents cascade

3. DEFENSE Overlay — Detailed Architecture

3.1 Threat Detection Pipeline

Incoming Request
  → IP reputation check (cached, TTL: 24h)
  → Rate limit enforcement (per-IP + per-key)
  → Payload validation (size + structure)
  → Behavioral analysis (pattern matching)
  → Risk score calculation (0.0–1.0)
  → Decision: ALLOW / CHALLENGE / BLOCK

4. Data Security

4.1 Database Access Control

All database tables use Row-Level Security (RLS) policies:

  • User-scoped tables: Access restricted to auth.uid() = user_id
  • Agency-scoped tables: Access restricted to agency membership
  • System tables: Read-only access via service role
  • Audit tables: Append-only — no UPDATE or DELETE policies

4.2 API Key Security

  • Keys stored as salted SHA-256 hashes — plaintext never persisted
  • Key prefix (8 chars) stored separately for identification
  • Keys have configurable expiration and scope limits
  • Revoked keys are soft-deleted with audit trail

4.3 Secrets Management

  • All API keys and tokens stored as encrypted environment variables
  • No secrets in source code — enforced by CI checks
  • Publishable/anon keys are the only exception (by design)

5.2 Canon Lock

Canon Lock is an architectural invariant that freezes core substrate architecture. When engaged, no EVOLUTION proposals can modify kernel, zone, or overlay definitions. Only execution-surface-level improvements are permitted.

5.3 Ethical Constraints

Every mutation passes through ethicalConstraintCheck():

  • Content safety validation (no harmful output generation)
  • Bias detection (statistical fairness checks)
  • Privacy impact assessment (PII exposure prevention)
  • Consent verification (dream pool sharing requires explicit opt-in)

6. Audit & Compliance

6.1 Hash-Chained Audit Log

The AUDIT zone maintains a tamper-evident log using hash chaining:

Record[N].hash = SHA-256(
  Record[N].id +
  Record[N].action +
  Record[N].entity +
  Record[N].timestamp +
  Record[N-1].hash
)

Any tampering with a historical record breaks the chain for all subsequent records, making modification detectable.

6.2 Immutable Incidents

Post-mortem records are sealed on creation:

  • No UPDATE or DELETE operations permitted
  • Sequential, gapless IDs prevent record removal
  • Full signal attribution: health, forecast, correlation data preserved

6.3 Governance Audit Ledger

All governance mode changes are recorded with:

  • Previous and new mode
  • Rationale (required for all non-ACTIVE transitions)
  • TTL and expected revert time
  • Initiator identity

7. Security Invariants

  1. No unbounded collections — Every in-memory structure has a hard cap
  2. No unvalidated input — All strings, numbers, and payloads checked at entry
  3. No silent crashes — Validation failures return safe defaults, never throw
  4. No cross-node cascade — Circuit breakers are independent per node
  5. No unaudited mutations — Every state change logged via AUDIT zone
  6. No unbounded evolution — SEBA framework + GOVERNANCE approval required
  7. No plaintext secrets — All credentials hashed or encrypted at rest
  8. No split-brain failover — Single-writer model prevents inconsistency
