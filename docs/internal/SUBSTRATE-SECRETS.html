1. System Overview

Substrate OS is a 14-module cognitive orchestration system that powers self-evolving, self-healing AI infrastructure. It's not a traditional application—it's a living system that learns, reflects, and improves itself.

The 14 Modules (5 Layers)

┌─────────────────────────────────────────────────────────────┐ │ ORCHESTRATOR LAYER │ │ CORTEX │ │ (Policy Intent, Governance, Evolution) │ ├─────────────────────────────────────────────────────────────┤ │ ADMINISTRATIVE LAYER │ │ SYSTEM MODERNIZER INTEGRATION INCLUSIVE │ │ (Backup, (Evolution, (Adapters, (WCAG, │ │ Heal) Proposals) Discovery) A11y) │ ├─────────────────────────────────────────────────────────────┤ │ OPERATIONAL LAYER │ │ DEFENSE NEXUS VISION │ │ (Security, (AI Routing, (Observability, │ │ Threats) Providers) Metrics) │ ├─────────────────────────────────────────────────────────────┤ │ COGNITIVE LAYER │ │ BRAIN DECODE DREAM │ │ (Memory, (Intent, (Nocturnal, │ │ Learning) Interface) Mutation) │ ├─────────────────────────────────────────────────────────────┤ │ KERNEL LAYER │ │ CORE RIPPLE ACCESS │ │ (Scheduler, (Event Bus, (API Keys, │ │ Lifecycle) Pub/Sub) Quotas) │ └─────────────────────────────────────────────────────────────┘
The Secret: Each module is independently health-scored (0-100) with its own circuit breaker. When a module degrades below 40%, the system triggers auto-healing without human intervention. This is why the system "never goes down"—it repairs itself before users notice problems.

2. The Evolution Engine (Modernizer)

The Evolution Engine is what makes Substrate OS self-improving. When someone asks "How does the system evolve itself?", this is the answer:

The 5-Phase Evolution Lifecycle

SCAN → PLAN → SHADOW → PRODUCTION → VERIFY │ │ │ │ │ │ │ │ │ └─ Health check + receipt │ │ │ └─ Real changes with backup │ │ └─ Test changes in isolation │ └─ Create normalized proposal └─ Cognitive analysis of system state

The Real Secret: Proposal Normalization Layer (v0.7.9)

Raw suggestions from cognitive scans are chaotic. The normalization layer forces them into a strict schema before any evolution can proceed:

{
  action_type: 'code_change' | 'config_update' | 'schema_migration',
  scope: 'module' | 'function' | 'file',
  risk_level: 'low' | 'medium' | 'high',
  confidence: 0.0 - 1.0,
  normalized: true  // MUST be true or evolution is blocked
}
The Secret: The evolution engine is hardcoded to refuse any plan not marked as normalized. This prevents garbage proposals from entering the system. If normalization fails, you get a clear terminal error—not a silent failure that corrupts state.

Confidence-Gated Autonomy

The system has 3 autonomy modes:

  1. Off: Human approval required for everything
  2. Advisory: System suggests changes but doesn't execute
  3. Governed: Auto-execute IF all conditions are met:
    • Confidence ≥ 80%
    • Risk level = "low"
    • No other evolution active
    • Previous run succeeded
    • Under daily limit
The Secret: Even in "governed" mode, a circuit breaker immediately opens (blocking all evolutions) if ANY production apply fails. The system cannot run away with failures—one mistake and it stops itself.

3. Cognitive Architecture (Brain Module)

The Brain is the memory and reasoning core. It's not a chatbot—it's a structured knowledge system with multiple specialized engines.

Three-Tier Memory System

┌─────────────────┐ │ HOT TIER │ ← Recently accessed, high-value memories │ (500 max) │ Accessed within 90 days ├─────────────────┤ │ WARM TIER │ ← Important but less frequently accessed │ (2,000 max) │ Intermediate storage ├─────────────────┤ │ COLD TIER │ ← Archived, compressed memories │ (10,000 max) │ Long-term storage, rarely accessed └─────────────────┘
The Secret: Memories automatically tier down based on a calculated "memory value score": 
value = (importance × 0.4) + (recency × 0.35) + (access_frequency × 0.25)
When hot tier overflows, lowest-value memories are demoted. This is why the system "remembers what matters"—it mathematically prioritizes.

The 5 Cognitive Engines

  1. Memory Core: 5-stage lifecycle (ingest → store → index → reflect → retrieve)
  2. Learning Engine: 5-stage loop (input → feedback → adjustment → reinforcement → stabilization)
  3. Imagination Engine: 4-stage generative (latent_extraction → recombination → simulation → synthesis)
  4. Reasoning Engine: 5-stage logic (causal_mapping → dependency_analysis → hypothesis_generation → validation → projection)
  5. Governance Guard: 3-stage ethics (coherence_validation → ethical_check → governance_signal)
The Secret: All engines route through a central Engine Bus (brain.engine_bus) that enforces execution ordering, manages retries, and normalizes error codes. No engine runs "directly"—everything is orchestrated.

4. Accessibility Pipeline (Inclusive Module)

When someone asks "How did you get the system to run accessibility blockers when creating templates?", this is the answer:

The 4-Stage A11y Pipeline

CRAWL → SCAN → ANALYZE → REPAIR │ │ │ │ │ │ │ └─ Generate fix suggestions │ │ └─ WCAG 2.2 compliance check │ └─ DOM/ARIA inspection └─ Page discovery & rendering

How Template Blocking Works

Before any template is published:

  1. The Inclusive module scans the rendered output
  2. Critical violations (Level A failures) trigger a BLOCK status
  3. The template cannot be published until issues are resolved
  4. Each issue includes an automated repair suggestion
The Secret: The scanner uses a weighted scoring system: 
score = 100 - (critical × 20) - (serious × 10) - (moderate × 5) - (minor × 1)
Templates must achieve a minimum score (typically 80+) to pass. This is why "perfect" accessibility is enforced—it's mathematically gated.

Repair Suggestions

The Secret: Each module has its own independent circuit breaker. If the BRAIN module fails 3 times in a row, only BRAIN is blocked—other modules continue operating. This isolation is why partial failures don't cascade into full outages.

Auto-Heal Trigger

  1. System automatically triggers system.heal
  2. Heal resets the module's health to 100
  3. Circuit breaker resets to CLOSED
  4. Event is logged to brain_events for auditing

7. Defense Perimeter Engine

Threat Scoring Pipeline

Every request is scored for threat level:

score = baseScore(fingerprint)
       + pathSensitivityModifier
       + velocityModifier(requests/hour)
       + cloudOriginModifier
       + reputationModifier

if (score >= 80) → BLOCK
if (score >= 60) → CHALLENGE
if (score >= 35) → MONITOR
else             → ALLOW
The Secret: The system maintains an IP reputation graph that persists across sessions. Known good actors accumulate positive reputation; bad actors are remembered. A returning scanner from a known-bad IP immediately scores +25 points toward blocking.

User-Agent Fingerprinting

Every request is classified into families:

  • chrome-desktop, safari-mobile → Low base score (10)
  • curl, python-requests → Medium score (45)
  • scanner, tor-exit → High score (85)
  • empty-ua → Suspicious score (70)

8. Backup & Recovery System

Failsafe Architecture

Every critical operation follows the pattern:

1. CREATE FAILSAFE BACKUP 2. EXECUTE OPERATION 3. IF (failure) → RESTORE FROM BACKUP 4. IF (success) → KEEP BACKUP FOR 30 DAYS
The Secret: The "permanent failsafe" is a special backup marked with is_permanent: true that is never auto-pruned. This is the absolute last resort—it can restore the entire system to a known-good state even if everything else fails.

What Gets Backed Up

  • Module health states and circuit breaker positions
  • Orchestrator state (phase, cycle count)
  • Data counts for integrity verification
  • SHA-256 checksum for tamper detection

Checksum Verification

checksumData = JSON.stringify({
  counts: data_counts,
  orchestrator: health_score,
  version: substrate_version,
  timestamp: epoch_ms
})
checksum = SHA256(checksumData).substring(0, 32)
