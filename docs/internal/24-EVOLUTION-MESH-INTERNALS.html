2. Exact Injection Detection Patterns

These are the production regex patterns used for threat detection:

SQL Injection Detection

const SQL_INJECT_RE = /(\b(SELECT|INSERT|UPDATE|DELETE|DROP|ALTER|UNION|CREATE|EXEC)\b\s)/i;

Behavior: Case-insensitive, word-boundary match. Requires a SQL keyword followed by whitespace. Used in both the validator (for archetype classification as injection_attempt) and in the repair engine (for SQL_SANITIZE strategy).

XSS Detection

const SCRIPT_RE = /<script[\s\S]*?<\/script>/gi;

Behavior: Global, case-insensitive. Matches complete script tag pairs including content. Used in the SANITIZE repair strategy to strip script blocks entirely.

Additional Threat Patterns

const CONTROL_CHAR_RE = /[\x00-\x08\x0B\x0C\x0E-\x1F]/g;
const ZERO_WIDTH_RE   = /[\u200B\u200C\u200D\uFEFF\u00AD\u2060\u180E]/g;
const DANGEROUS_KEYS  = new Set(['__proto__', 'constructor', 'prototype']);

4. Archetype Classification Algorithm

Repairability Gate

REPAIRABLE_ARCHETYPES = Set(['type_mismatch', 'missing_required'])

// All others safe-fail immediately:
// empty_shell, oversized, injection_attempt, shape_alien
// partial_valid → context-dependent (falls through to repair attempt)

Classification Priority Logic

1. If zero issues → 'well_formed'
2. If zero recognized keys → 'shape_alien'
3. If size issues ≥ 50% of total issues → 'oversized'
4. If type issues ≥ 50% of total issues → 'type_mismatch'
5. If missing issues ≥ 50% of total issues → 'missing_required'
6. Else → 'partial_valid'

Note: 'injection_attempt' is classified BEFORE this function,
in the validator, via regex detection. It short-circuits all
other classification.

Confidence Scoring Formula

confidence = issues.length === 0
  ? 1.0
  : Math.max(0.1, 1 - issues.length * 0.15)

// Each issue reduces confidence by 15%
// Floor at 0.1 (never zero for non-empty input)

5. Learning Rule Engine — Complete Internals

Rule Structure

interface LearnedRule {
  id: string;              // 'rule_1', 'rule_2', ...
  repairStrategy: string;  // e.g., 'COERCE_TYPE'
  archetype: string;       // e.g., 'type_mismatch'
  confidence: number;      // 0.0 – 1.0
  sourceFunction: string;  // which fn generated this rule
  category: string;        // 'general', 'security', etc.
  invocations: number;     // how many times applied
  successes: number;       // how many times it helped
  createdAt: number;       // timestamp
}

Confidence Thresholds (CRITICAL)

Minimum to create rule>= 0.6Only high-confidence repairs become rules
Minimum to apply rule> 0.4Rules below this are skipped during lookup
Auto-demote threshold< 0.3 AND > 10 invocationsRule is deleted from registry
Confidence boost on success+0.02Capped at 1.0
Confidence penalty on failure-0.05Floored at 0.0
Max rules per lookup5Top-5 by confidence, filtered by category

Key insight: Failure penalty (−0.05) is 2.5× stronger than success boost (+0.02). This ensures low-quality rules are demoted faster than they can be promoted, preventing noise accumulation.

6. Wrap Execution Pipeline — Complete Flow

Phase 1: Preflight

1. Check meshConfig.enabled → if false, passthrough directly
2. validateInput(schema, input) → ValidationReport
3. If report.valid → go to Phase 2 (Execute)
4. If !report.valid:
   a. isRepairable(archetype)?
      - NO → Safe-fail (log, track, throw/callback)
      - YES → deterministicRepair(input)
        → If repaired: apply learned rules → execute → track
        → If repair fails at execution: safe-fail
        → If no repair strategy found: safe-fail

Phase 2: Execute

5. Execute fn(input)
6. If success → recordOutcome('success') → return result
7. If error:
   a. Re-validate input (second chance)
   b. If re-validation finds repairable archetype:
      → deterministicRepair(input)
      → Retry execution with repaired input
      → If retry succeeds → recordOutcome('repaired_success')
      → If retry fails → fall through to escalation
   c. Escalate: logger.error() → recordOutcome('escalated') → throw

Key detail: The "second chance" re-validation at step 7a means even inputs that initially passed validation can be repaired after an execution error. This catches edge cases where the schema says "valid" but the downstream handler disagrees.

12. Known Limitations & Future Work

  • Repair strategies: 12 of planned 29+ are implemented. Missing: JSON_FALLBACK, ENUM_CLAMP (partial), URL_NORMALIZE, EMOJI_FLOOD_COLLAPSE
  • Shadow equality: Uses JSON.stringify comparison. Deep structural diff is a planned premium feature
  • Rule application: applyRule() currently returns { applied: false } — rules inform strategy selection but don't directly transform. Direct rule-based transforms are planned
  • Repair counter: repairSuccessCount always equals repairCount because success is determined by strategy application, not downstream execution success. Needs decoupling
  • requiredOneOf: Validator supports requiredOneOf groups but repair engine doesn't know how to generate missing values from related fields
