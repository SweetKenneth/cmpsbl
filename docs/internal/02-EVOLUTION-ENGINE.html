🔄 Evolution Engine (Modernizer)

How the System Improves Itself — The Complete Picture

What Makes Evolution Work?

The Evolution Engine is the system that allows Substrate OS to autonomously identify problems and apply fixes. When someone asks "How does the system evolve itself?", this is the complete answer.

🔐 The Core Secret: Evolution is NOT magic AI. It's a deterministic pipeline with strict gates at every step. Raw AI suggestions are forced through a normalization layer that converts them into typed, validated actions. The system cannot execute anything that hasn't passed all validation gates.

The 5-Phase Evolution Lifecycle

┌─────────────────────────────────────────────────────────────────────────┐ │ EVOLUTION LIFECYCLE │ ├─────────────────────────────────────────────────────────────────────────┤ │ │ │ ┌──────┐ ┌──────┐ ┌────────┐ ┌────────────┐ ┌────────┐ │ │ │ SCAN │───►│ PLAN │───►│ SHADOW │───►│ PRODUCTION │───►│ VERIFY │ │ │ └──────┘ └──────┘ └────────┘ └────────────┘ └────────┘ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ │ ▼ ▼ ▼ ▼ ▼ │ │ Analyze Normalize Test in Apply with Health │ │ 3 sources proposals isolation backup check │ │ │ │ [aborted] or [failed] can be reached from ANY phase │ └─────────────────────────────────────────────────────────────────────────┘

Phase 1: SCAN (Cognitive Analysis)

The scan phase synthesizes data from 3 independent sources:

  1. Phase A (Edge Analysis): Inspects deployed edge functions, finds archived/repurposed code
  2. Phase B (System State): Checks evolution state, circuit breakers, stuck runs, anomalies
  3. Phase C (Code Health): Stability score, security posture, upgrade pressure
  4. Phase D (LLM Synthesis): AI-powered reasoning over all gathered data

Output: Raw proposals with varying confidence levels

Phase 2: PLAN (Normalization Layer)

This is the critical gate. Raw proposals are forced into a strict schema:

{
  action_type: 'code_change' | 'config_update' | 'schema_migration' | 'function_toggle',
  scope: 'module' | 'function' | 'file' | 'config',
  risk_level: 'low' | 'medium' | 'high',
  confidence: 0.0 - 1.0,
  target_file?: string,
  description: string,
  normalized: true  // MUST be true to proceed
}

If normalization fails, the proposal is rejected and cannot enter the plan.

Phase 3: SHADOW (Isolated Testing)

Changes are applied to a shadow store—not production. This includes:

  • Writing artifacts to shadow store (in-memory or temp storage)
  • Running validation tests against shadow state
  • Creating a receipt documenting exactly what was done

Key: If shadow fails, production is never touched.

Phase 4: PRODUCTION (Gated Apply)

Production apply has multiple gates:

  1. Phase Gate: Must be in shadow_applied phase
  2. Verification Gate: Shadow artifacts must exist and be valid
  3. Backup Gate: Failsafe backup created BEFORE apply
  4. Atomicity Gate: Phase transition is atomic

If ANY gate fails → automatic rollback + mark run as failed.

Phase 5: VERIFY (Health Confirmation)

After production apply:

  • System health is re-measured
  • Health before/after is compared
  • If health degraded significantly, flag for review
  • Final receipt is created with complete audit trail

Evolution Receipts

Every shadow and production apply generates an immutable receipt:

// Receipt structure
{
  receipt_id: "uuid",
  run_id: "uuid",
  plan_id: "uuid",
  phase: "shadow_applied" | "production_applied",
  changes_applied: [
    { file_path: "...", operation: "create" | "update" | "delete", diff_summary: "..." }
  ],
  tests_run: 4,
  tests_passed: 4,
  health_before: { overall_score: 0.92, module_health: {...} },
  health_after: { overall_score: 0.95, module_health: {...} },
  backup_id: "uuid",
  timestamp: "ISO8601"
}
🔐 The Secret: Receipts are write-once. There is no UPDATE or DELETE on the receipts table. This creates an immutable audit trail that cannot be tampered with—essential for compliance and debugging.

Confidence-Gated Autonomy

The system has 3 autonomy modes that control how much human approval is needed:

ModeBehaviorWhen to Use
off Human approval required for everything Initial deployment, untrusted environments
advisory System suggests changes but never executes Learning phase, monitoring only
governed Auto-execute IF all conditions met Mature systems with proven track record

Governed Mode Requirements

For a proposal to auto-execute in governed mode, ALL conditions must be true:

  • ✅ Confidence score ≥ 80%
  • ✅ Risk level = "low"
  • ✅ No other evolution currently active
  • ✅ Previous run succeeded (no recent failures)
  • ✅ Under daily evolution limit
  • ✅ Evolution circuit is CLOSED (not tripped)
⚠️ Critical Safety: Even in governed mode, a circuit breaker immediately opens if ANY production apply fails. One mistake and the system stops itself—it cannot run away with failures.

Terminal Commands Reference

// Status & inspection
modernizer.status          // Current evolution status
modernizer.jobs            // List all evolution runs
modernizer.receipts        // List recent receipts with full details

// Evolution lifecycle
modernizer.scan            // Run cognitive scan
modernizer.scan --explain  // Scan with detailed explanations
modernizer.scan --llm-report  // Include AI recommendations

modernizer.evolve shadow   // Apply changes to shadow
modernizer.evolve production  // Apply to production (gated)
modernizer.evolve verify   // Verify and complete
modernizer.evolve abort    // Abort active evolution

// Circuit management
modernizer.circuit status  // Check circuit state
modernizer.circuit reset   // Reset (close) circuit
modernizer.circuit trip    // Force open (block evolutions)

// Autonomy control
modernizer.autonomy status // Check autonomy mode
modernizer.autonomy set off|advisory|governed
