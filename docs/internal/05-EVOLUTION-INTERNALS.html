PART A — SEBA Evolution Pipeline (12-Step Internal)

Public docs describe a 7-step lifecycle. The actual pipeline has 12 steps:

 1. VISION detects opportunity (anomaly or trend)
 2. VISION scores opportunity (impact × confidence × feasibility)
 3. MODERNIZER generates proposal with diff
 4. CORTEX checks governance bounds
 5. SANDBOX creates isolated test environment
 6. SANDBOX applies proposal in isolation
 7. SANDBOX runs regression suite (>85% pass required)
 8. SANDBOX runs performance benchmark (no >10% degradation)
 9. CORTEX evaluates risk score
10. APPROVAL (per autonomy tier)
11. MODERNIZER applies to production
12. MODERNIZER generates evolution stamp

Opportunity Scoring (Step 2)

opportunity_score = impact × confidence × feasibility
Threshold: opportunity_score >= 0.25 to proceed

Risk Scoring (Step 9)

risk_score = (1 - regression_pass_rate) × 0.4
           + performance_degradation     × 0.3
           + scope_breadth               × 0.2
           + reversibility_cost          × 0.1

scope_breadth = modules_affected / 21
Gate: risk_score > 0.6 → AUTOMATIC REJECTION

B.2 Promotion Pipeline Flow

1. Check isShadowMeshEnabled() guard
2. Capture shadow baseline snapshot (captureSnapshot)
3. Run shadow storm simulation
4. Capture post-shadow snapshot
5. Generate full diff (generateDiff)
6. Run pre_promote integrity scan
7. Execute preflight guardrails
8. If all pass → create production_promotions record
9. Canary stage: verify recent invocation success rate
10. Verification stage: confirm metrics stability
11. If pass → code stamp modified files + mark success
12. If fail at any stage → atomic rollback to pre_promote snapshot

B.4 Integrity Scanner Checks

STRUCTURAL CHECKS:
- Rule conflict detection (overlapping trigger conditions)
- Dormant rule identification (>30 days without invocation)
- Rollback instability (>3 rollbacks in recent history)

TELEMETRY CHECKS:
- Escalation spike detection (>15% of invocations)
- Latency creep detection (p95 > threshold)
- Oscillation detection (rule toggling between states)

REGISTRY CHECKS:
- Duplicate rule signature detection
- Executor registry mismatch (rules without valid executor)

Scoring:
  health_score = 100 - (criticals × 15) - (warnings × 5)
  Clamped to 0–100

B.5 Lifecycle Sweep (Automated Rule Transitions)

sweepRuleLifecycle() automates:
  learned → candidate:     if invocations >= 5 AND success_rate >= 0.6
  candidate → promoted:    if invocations >= 20 AND success_rate >= 0.8
  promoted → candidate:    if success_rate drops < 0.5 (demotion)
  any → retired:           if no invocations in 30+ days AND success_rate < 0.3
  conflict → blocked:      if conflicts detected during scan

B.7 Canary Verification

Canary check queries recent rule invocations (last 50):
  - Calculates success rate from invocation outcomes
  - Threshold: success_rate >= 0.7 to pass canary
  - If insufficient data (<5 invocations): auto-pass
  - Failed canary → immediate rollback

B.8 Rollback Semantics

Rollback restores from pre_promote snapshot:
  - Rule state (all immune rules)
  - Executor state (all executor health)
  - Metrics baseline
  - No partial state transitions permitted

Rollback triggers:
  - Canary failure
  - Verification failure
  - Integrity scan failure during promotion
  - Manual operator override

B.9 Telemetry Recording

system_metrics_history records:
  - success_rate: from rule invocations (successful / total)
  - escalation_rate: invocations requiring ENCODE assistance / total
  - encode_assist_rate: computed from escalation data
  - latency_p95: 95th percentile of invocation durations
  - cost_index: average cost per invocation in millicents
  - integrity_health_score: from most recent integrity scan
  - rule_count / promoted_rule_count / retired_rule_count
  - rollback_count: total rollbacks recorded
  - avg_executor_health: average across all executors

Recording frequency: on promote, on rollback, on demand
Retention: 30 days minimum
