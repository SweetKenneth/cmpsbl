PART I — SEBA (Self-Evolving Bounded Agent)

Architecture

9 Analysis Engines → Proposal Generation → Governance Gate → Execution

Core 4: Memory, Learning, Imagination, Reasoning
Extended 5: Security, Telemetry, Governance, Resources, Architecture

Sub-modules:
  - CognitiveAnalyzer — Scans for improvement opportunities
  - ProposalGenerator — Creates typed improvement proposals
  - GovernanceGate — Evaluates safety/coherence/ethics
  - EvolutionExecutor — Shadow→production execution
  - ProposalStore — Database persistence
  - EvolutionStampGenerator — Traceability stamps
  - LLMAnalyzer — AI-enhanced impact prediction

5 Operating Modes

ModeBehavior
offSEBA disabled
observeScans and logs proposals only
advisoryProposes improvements, requires human approval (DEFAULT)
governedAuto-executes if governance approves AND confidence ≥ threshold
autonomousFull autonomy within bounds (requires explicit unlock)

SEBA Cycle (5 Phases)

Phase 1: COGNIZING
  - CognitiveAnalyzer runs 9 analysis engines
  - Produces CognitiveInsight[] (type, confidence, urgency, evidence)
  - If no insights → cycle ends early

Phase 2: PROPOSING
  - ProposalGenerator converts insights to ImprovementProposal[]
  - Each proposal: category, risk_level, confidence_score, proposed_actions
  - Persisted to database via ProposalStore.storeBatch()

Phase 3: EVALUATING → GATING
  - GovernanceGate.evaluate(proposal)
  - Checks: coherence_score, ethical_score, risk_assessment, safety_score
  - Decision: approve | approve_with_conditions | defer | reject | escalate

Phase 4: APPLYING
  - Only if canAutoExecute() OR mode=autonomous
  - EvolutionExecutor runs shadow → production pipeline
  - Creates EvolutionStamps for traceability
  - Updates proposal status in database

Phase 5: VERIFYING
  - Health delta check
  - If health_delta < -max_health_degradation → auto-rollback

PART II — IMMUNITY MESH PROMOTION PIPELINE (SPARTA Epoch)

The promotion pipeline adds a governed mutation runtime on top of SEBA. Behavioral immune rules progress through a lifecycle with multi-gate validation at every stage.

2. Promotion Flow (12 Steps)

 1. Guard: isShadowMeshEnabled() must return true
 2. Capture shadow baseline snapshot
 3. Run shadow storm simulation (executeShadowStorm)
 4. Capture post-shadow snapshot
 5. Generate full diff (rules, metrics, executors, files)
 6. Run pre_promote integrity scan
 7. Execute preflight guardrails (6 checks)
 8. Create production_promotions record (status: pending)
 9. Canary stage: verify recent invocation success rate ≥ 0.7
10. Verification stage: confirm metrics stability
11. Success path: code stamp files + mark promotion success
12. Failure path: atomic rollback to pre_promote snapshot

4. Integrity Scanner

CHECKS PERFORMED:
  1. Rule conflict detection (overlapping triggers)
  2. Dormant rule detection (>30 days idle)
  3. Rollback instability (>3 recent rollbacks)
  4. Escalation spike (>15% of invocations)
  5. Latency creep (p95 above threshold)
  6. Oscillation detection (rules toggling states)
  7. Duplicate rule signatures
  8. Executor registry mismatch

SCORING:
  health_score = 100 - (criticals × 15) - (warnings × 5)
  Clamped to 0–100
  
  Critical findings: rule conflicts, executor mismatches
  Warning findings: dormant rules, escalation spikes, latency creep

5. Lifecycle Sweep (Automated Rule Transitions)

sweepRuleLifecycle() runs automatically and transitions rules:

  learned → candidate:
    Condition: invocations >= 5 AND success_rate >= 0.6

  candidate → promoted:
    Condition: invocations >= 20 AND success_rate >= 0.8

  promoted → candidate (demotion):
    Condition: success_rate drops below 0.5

  any → retired:
    Condition: no invocations in 30+ days AND success_rate < 0.3

  conflict → blocked:
    Condition: integrity scan detects active conflicts

Source: src/lib/immune/rule-engine/lifecycle-sweep.ts

7. Canary Verification

Query: last 50 rule invocations
Calculate: success_rate = successful / total
Threshold: success_rate >= 0.7
If data < 5 invocations: auto-pass (insufficient data)
Failure: immediate rollback + mutation_receipt logged

8. Rollback

Deterministic rollback restores from pre_promote snapshot:
  - All immune rules (status, invocations, scores)
  - All executor health records
  - Metrics baseline
  - No partial state transitions

Triggers:
  - Canary failure
  - Verification failure
  - Integrity scan critical during promotion
  - Manual operator override

Post-rollback:
  - mutation_receipt logged with stage='rollback'
  - production_promotions marked as rolled_back
  - system_metrics_history updated

9. Telemetry

system_metrics_history records:

  success_rate:         successful_invocations / total_invocations
  escalation_rate:      escalated_invocations / total_invocations
  encode_assist_rate:   computed from escalation data
  latency_p95:          95th percentile of invocation durations (ms)
  cost_index:           avg cost per invocation (millicents)
  integrity_health_score: from most recent integrity scan
  rule_count:           total active rules
  promoted_rule_count:  rules in 'promoted' status
  retired_rule_count:   rules in 'retired' status
  rollback_count:       total rollbacks recorded
  avg_executor_health:  average across all executors

Recording: on promote, on rollback, on demand
Retention: 30 days minimum
Dashboard views: 24h, 7d, 30d
Export: JSON, CSV

10. Scoring Algorithms

Dominant Score:
  dominantScore = (successRate × 40) + (invocations × 0.5) + (1 - escalationRate) × 20
  Clamped 0–100

Risk Score:
  riskScore = (escalationRate × 30) + ((1 - successRate) × 40) + (conflictCount × 10)
  Clamped 0–100

Spread Velocity:
  spreadVelocity = (crossExecutorHits × 2) + (sharedRuleContributions × 3)
  Clamped 0–100

Rule Health:
  ruleHealth = (successRate × 50) + ((1 - escalationRate) × 30) + (invocations > 0 ? 20 : 0)
  Clamped 0–100
