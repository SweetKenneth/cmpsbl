## Abstract

This paper presents *Ascension*, a deterministic software evolution engine that discovers emergent capabilities by colliding uploaded source code against a fixed 40-primitive cognitive substrate matrix. Unlike generative AI systems that produce code from prompts, Ascension preserves the developer's original logic and wraps it in a discovered cognitive overlay — producing portable, zero-dependency artifacts in 25 programming languages including 7 hardware description languages. The system operates without external AI API calls; all discovery, scoring, and export processes are purely algorithmic. We describe the complete 8-stage transformation pipeline, the Crown Jewel Pipeline Index (CJPI) scoring methodology, the Capability Affinity System for archetype-aware filtering, the dual-layer execution model, and the IP protection mechanisms including hex-encoded weight obfuscation. A real-world case study demonstrates the system processing an OpenAI-pattern PHP agent, where the substrate autonomously discovered 5 distinct capability futures — including sovereign governance and ghost defense — with a combined floor valuation of approximately $2.6M. This paper is published as a prior art disclosure to establish the priority date of these inventions.

**Keywords:** software evolution, capability discovery, cognitive substrate, deterministic transformation, cross-language export, prior art, intellectual property protection, primitive collision, CJPI scoring

## 1. Introduction

### 1.1 Problem Statement

Modern software development produces functional code that operates within the boundaries of its original design intent. A trading bot executes trades; a web scraper collects data; an API gateway routes requests. The latent capability potential of these programs — what they *could become* when augmented with orthogonal cognitive capabilities — remains unexplored.

Existing approaches to software augmentation fall into two categories: (1) generative AI systems that produce new code from natural language prompts, replacing or rewriting original logic; and (2) library/framework ecosystems that require manual integration by developers. Neither approach preserves the original code's identity while systematically discovering what new capabilities emerge when that code's behavioral surface is combined with a structured capability matrix.

### 1.2 Contribution

Ascension introduces a third paradigm: **deterministic software evolution**. The system:

1. Accepts any working source code in 25 supported languages
2. Derives a capability surface from the code's actual structure (function signatures, domain signals, behavioral patterns)
3. Registers this surface as a first-class participant ("Primitive #41" or "Auxiliary Primitive Ψ₄₁") in a fixed 40-primitive substrate matrix
4. Executes multi-chain collisions between the Auxiliary Primitive and all 40 substrate primitives
5. Scores each discovered combination using the Crown Jewel Pipeline Index (CJPI)
6. Exports selected discoveries as portable, single-file artifacts with an embedded mini-runtime engine
7. Protects intellectual property through hex-encoded CJPI weights, stripped comments, and genericized naming

The entire process requires **zero external AI API calls**. All discovery is algorithmic, deterministic (given the same input code and substrate version), and auditable through cryptographic fingerprinting.

### 2.2 The Cross-Sector Synergy Matrix

Collisions between primitives from different sectors produce synergy bonuses that reflect the architectural insight that cross-domain combinations yield disproportionate emergent value. The synergy matrix is a lookup table of scored sector pairs:

```

──────────────────────────────────────────

ccr + csz            → 7
ccr + execution      → 4
ccr + shell          → 5
execution + esz      → 4
execution + csz      → 5
execution + field    → 3

esz + shell          → 5

emz + execution      → 3

epz + csz            → 6

```

In addition, user-domain sectors (derived from the uploaded code's classification) interact with substrate sectors:

```
────────────────────────────────────────────

data + ccr                      → 7
data + emz                      → 6
hardware + execution            → 6
hardware + core                 → 5
hardware + field                → 5
hardware + shell                → 5
```

The synergy computation for multi-sector chains uses the following algorithm:

```
function getSectorSynergy(sectors: string[]): number {
    unique = deduplicate(sectors)
    if unique.length < 2: return 0
    
    totalSynergy = 0
    for each pair (i, j) in unique:
        key1 = unique[i] + "+" + unique[j]
        key2 = unique[j] + "+" + unique[i]
        totalSynergy += lookup(key1) || lookup(key2) || 3  // default synergy = 3
    
    pairCount = (unique.length * (unique.length - 1)) / 2
    return floor(totalSynergy / max(1, sqrt(pairCount)))
}
```

The square-root normalization prevents long chains from producing runaway synergy scores while still rewarding genuine cross-sector diversity.

## 3. The Auxiliary Primitive (Ψ₄₁) — Capability Surface Derivation

### 3.1 Overview

When a developer uploads source code, the Ascension engine does not treat it as passive input to be analyzed. Instead, it derives a **Capability Surface** — a structured profile identical in shape to the 40 substrate primitives — making the uploaded code a first-class participant in the collision engine. This is designated "Primitive #41" or "Auxiliary Primitive Ψ₄₁."

### 3.2 Capability Surface Structure

The derived surface has the following fields:

```typescript
interface CapabilitySurface {
    nodeName: string;        // e.g., "TRADE_ENGINE", "DATA_PIPELINE"
    capabilities: string[];  // exactly 4 verbs, like substrate primitives
    sector: string;          // maps into the synergy matrix
    description: string;     // human-readable label
    components: string[];    // extracted function/class names (up to 12)
    domain: string;          // raw domain classification
}
```

### 3.3 Domain Detection Algorithm

The system classifies uploaded code into one of 12 functional domains using a weighted keyword signal analysis:

| Domain | Signal Keywords |
|--------|----------------|
| `trading` | trade, order, ticker, exchange, position, portfolio |
| `finance` | balance, ledger, payment, invoice, accounting |
| `web` | react, component, html, css, dom, render |
| `api` | endpoint, fetch, api, rest, graphql, request |
| `data` | dataframe, csv, transform, pipeline, etl, aggregate |
| `ml` | model, train, predict, tensor, neural, loss |
| `security` | encrypt, auth, token, jwt, certificate, firewall |
| `automation` | automat, schedule, cron, task, workflow, queue |
| `iot` | sensor, mqtt, gpio, device, telemetry, actuator |
| `game` | game, sprite, render, physics, collision, player |
| `hardware` | verilog, vhdl, module, wire, reg, clock, synthesis, fpga, signal, assign |
| `software` | (fallback) |

Each keyword match in the code content scores +2; keyword matches in the filename score +3. Hardware description languages receive an additional +10 bonus based on the language identifier. The domain with the highest aggregate score is selected.

### 3.5 Verb Extraction from Source Code

The system extracts actual function/method names from the uploaded code using language-agnostic regex patterns:

```
Pattern Set:
    /(?:export\s+)?(?:async\s+)?function\s+([a-zA-Z_]\w{2,})/g    // JS/TS
    /(?:pub\s+)?fn\s+([a-z_]\w{2,})/g                              // Rust
    /def\s+([a-z_]\w{2,})/g                                        // Python/Ruby
    /module\s+([A-Za-z_]\w{2,})/g                                  // HDL
    /const\s+([a-zA-Z_]\w{2,})\s*=/g                               // JS/TS constants
```

Extracted names are decomposed from camelCase/snake_case into constituent words, and the first word of each (assumed to be a verb) is frequency-counted. The top 4 most-frequent verbs replace the domain defaults if at least 3 verbs are extracted, ensuring the Auxiliary Primitive's capability surface reflects the *actual behavior* of the uploaded code rather than generic domain assumptions.

### 3.6 Component Extraction

Up to 12 function/class/module names are extracted from the source to populate the `components` array. These are surfaced in the discovery descriptions to maintain provenance: users can see exactly which parts of their code contributed to each discovered capability.

## 4. Archetype Classification and Capability Affinity System

### 4.1 Software Archetype Classification

Before collision execution, the uploaded code is classified into one of three software archetypes:

| Archetype | Description | Examples |
|-----------|-------------|----------|
| **Active** | Long-running processes with event loops, state machines, or daemon behavior | Agents, bots, workers, cron jobs, IoT devices |
| **Passive** | Render-focused code without runtime loops | UIs, static sites, component libraries |
| **Hybrid** | Request/response patterns with mixed concerns | APIs, CLI tools, services |

Classification uses a weighted signal analysis of code content:

**Active signals** (with weights):
- `setinterval` (3), `event_loop` (4), `while true` (4), `cron` (3), `worker` (3), `daemon` (4), `agent` (3), `websocket` (3), `tokio::spawn` (4), `goroutine` (3), `state_machine` (3)

**Passive signals:**
- `react` (3), `component` (2), `render` (3), `<div` (3), `usestate` (3), `vue` (3), `svelte` (3), `stylesheet` (3)

The ratio of active-to-total signals determines the classification:
- Active ratio > 0.65 → **Active**
- Active ratio < 0.35 → **Passive**
- Otherwise → **Hybrid**

Hardware description languages (Verilog, VHDL, SystemVerilog, Chisel, SPICE) always receive +5 to the active score, reflecting that HDL describes inherently always-running circuits.

### 4.2 Hard Filtering (Incompatible Primitives)

Based on the archetype, certain substrate primitives are excluded from the collision sweep:

- **Active code excludes:** VISION, INCLUSIVE (no UI rendering context)
- **Passive code excludes:** DREAM, NEXUS, CORTEX, HARVEST, EVOLUTION, SANDBOX, PHANTOM, ECHO, REFLEX (no runtime loop context)
- **Hybrid code:** No exclusions — all 40 primitives participate

This hard filtering reduces wasted collisions by approximately 30% for non-hybrid code.

### 4.3 Soft Weighting (Affinity Boosts)

Beyond hard filtering, primitives that are particularly well-suited to each archetype receive a CJPI score boost of +2 to +3 points:

| Archetype | Boosted Primitives |
|-----------|--------------------|
| Active | DREAM (+3), CORTEX (+3), EVOLUTION (+3), NEXUS (+2), HARVEST (+2), REFLEX (+2), ECHO (+2), PHANTOM (+2), SANDBOX (+2), NERVE (+2) |
| Passive | VISION (+3), INCLUSIVE (+3), IDENTITY (+2), RELAY (+2), FORGE (+2), COMPASS (+2), LINGUA (+2), ACCESS (+2) |

## 5. The Multi-Chain Collision Engine

### 5.1 Collision Mechanics

The collision engine tests the Auxiliary Primitive (Ψ₄₁) against each substrate primitive, generating scored capability discoveries at multiple chain depths (2 to 8 nodes).

#### 5.1.1 Two-Node Chains (Ψ₄₁ + Target)

For each of the target primitive's 4 capability verbs:

```
nameHash = hash(surface.nodeName + ":" + targetNode + ":" + capabilityVerb + ":v4")
baseCjpi = 20 + (nameHash % 29)            // Range: 20-48
synergy  = getSectorSynergy([candidateSector, targetSector])
variance = ((nameHash >> 8) % 9) - 4       // Range: -4 to +4
affinityBoost = getArchetypeBoost(archetype, targetNode)

cjpi = baseCjpi + traitBonus + synergy + variance + affinityBoost
cjpi = clamp(cjpi, 25, 72)                 // 2-node cap
```

Only discoveries with `cjpi >= 30` are retained. Furthermore, only discoveries that match a named archetype in the chain archetype registry are surfaced — generic chain names are discarded as noise.

#### 5.1.2 Multi-Node Chains (3-8 Nodes)

For chains of length 3 to `min(8, permutationDepth + 2)`:

1. Partners are selected deterministically using hash-based indexing
2. 70% of partners are drawn from cross-sector nodes; 30% from same-sector nodes
3. Scoring formula:

```
baseScore      = 15 + (chainHash % 24)
depthBonus     = (chainLength - 2) × 3
diversityBonus = (uniqueSectorCount - 1) × 2
variance       = ((chainHash >> 8) % 13) - 6
chainAffinity  = sum(archetypeBoost for each partner node)

cjpi = baseScore + synergy + depthBonus + diversityBonus + traitBonus + variance + chainAffinity
```

Maximum CJPI by chain depth:

| Chain Depth | Maximum CJPI |
|-------------|-------------|
| 3 nodes | 78 |
| 4 nodes | 86 |
| 5 nodes | 92 |
| 6 nodes | 96 |
| 7 nodes | 98 |
| 8 nodes | 99 |

Only discoveries with `cjpi >= 35` and a matching named archetype are retained.

### 5.2 Trait Bonus (Developer Code Quality)

The Auxiliary Primitive receives a trait bonus (capped at 5) based on code characteristics:

| Condition | Bonus |
|-----------|-------|
| Resolver count > 15 | +2 |
| File size > 100 KB | +1 |
| Capability verbs ≥ 4 | +1 |
| Resolver count > 30 | +1 |

## 6. CJPI Scoring and Tier Classification

### 6.1 Crown Jewel Pipeline Index (CJPI)

The CJPI is a composite score from 0-99 that evaluates the quality of a discovered capability across four dimensions:

| Factor | Description |
|--------|-------------|
| **Novelty** | How unique is this combination? (reflected in hash-based base scoring) |
| **Utility** | How practical is the result? (reflected in archetype matching — only named patterns surface) |
| **Complexity** | How sophisticated is the interaction? (reflected in chain depth bonus) |
| **Composability** | Can this be combined with other discoveries? (reflected in cross-sector synergy score) |

### 6.2 Tier Classification

| Tier | CJPI Range | Significance |
|------|-----------|--------------|
| **APEX** | 92-99 | Highest-tier discovery; architecturally transformative |
| **MYTHIC** | 80-91 | Major capability enhancement |
| **RELIC** | 65-79 | Significant cross-domain augmentation |
| **PRIME** | 45-64 | Practical capability addition |
| **MINT** | 25-44 | Lightweight enhancement |

### 6.3 Structural Fingerprinting

Every discovery receives a SHA-256 structural fingerprint computed from its chain composition:

```
fingerprint = SHA-256(JSON.stringify({
    steps: chain.map(module => ({ module, capability: "collision" })),
    epoch: "SPARTA"
}))
```

This fingerprint serves as a tamper-evident identifier: if the discovery chain is modified, the fingerprint changes. Fingerprints are truncated to 12 uppercase hex characters for display but the full 64-character hash is stored.

### 6.4 Moat Signature

Upon ascension (locking a discovery), each capability receives a cryptographically random UUID as a `moat_signature`. This serves as a unique provenance identifier that cannot be derived from the discovery parameters, providing an additional layer of authenticity verification.

## 7. The Capability Marketplace

### 7.1 Interactive Selection Model

After the collision sweep completes, discoveries are not automatically exported. Instead, they are surfaced in a **Capability Marketplace** — an interactive catalog where developers review, select, and curate their capability composition before export.

### 7.2 Dynamic Bundle Clustering

Discoveries are automatically clustered into dynamic bundles using a composite key of `primarySubstrateNode + depthTier`:

- **Shallow** (depth ≤ 2): Direct augmentations
- **Mid** (depth 3-4): Cross-domain fusions
- **Deep** (depth ≥ 5): Architectural transformations

Micro-clusters (single-capability bundles) are merged into the nearest bundle by node overlap, preventing fragmentation.

### 7.3 Impact Classification

Each bundle receives an impact tier:

| Impact Tier | Criteria |
|-------------|----------|
| Enhancement | Average chain depth ≤ 2 |
| System Upgrade | Average chain depth 3-4 |
| Architectural Shift | Average chain depth ≥ 5 |

### 7.4 Composition Coherence Scoring

The Marketplace computes a real-time **Composition Coherence** score (0-100%) for the selected capability set:

```
coherence = 100
if deep_chains > 3: coherence -= (deep_chains - 3) × 15
if unique_nodes > 15: coherence -= (unique_nodes - 15) × 3
coherence = clamp(coherence, 0, 100)
```

This guides developers toward selecting coherent capability sets rather than accumulating unrelated discoveries that would produce fragile exports.

## 8. The Dual-Layer Execution Model

### 8.1 Architecture

Every Ascension export employs a dual-layer execution model:

**Layer 1 — Native Execution:**
The developer's original source code runs first, unchanged. Not a single line of the original logic is modified. The code executes in its native language runtime exactly as it did before Ascension.

**Layer 2 — Cognitive Overlay:**
The discovered substrate primitives execute in sequence after the native layer, enriching the response object with discovered capabilities. The overlay reads from the native layer's outputs and adds cognitive augmentations without modifying the original execution path.

### 8.2 Design Rationale

This architecture provides:

1. **Preservation guarantee:** The original code is never modified
2. **Portability:** If the substrate disappears, Layer 1 still functions
3. **Debuggability:** Original behavior is isolated from augmented behavior
4. **Rollback safety:** Removing the cognitive overlay restores exact original functionality

## 9. Export and IP Protection

### 9.1 The CMPSBL® Sealed Runtime™

Exports are packaged as ZIP archives containing:

1. **Original source code** — untouched, in the developer's import language
2. **`standalone-runtime.ts`** (or language equivalent) — Mini-Runtime Engine
3. **`chain-executor.ts`** — Discovers and executes capability chains
4. **`discovery-engine.ts`** — Substrate discovery logic
5. **`manifest.json`** — Pack metadata including CJPI scores, fingerprints, and moat signatures
6. **Auto-generated documentation** — Capability descriptions and execution traces
7. **Test bench** — Validation harness for the exported capabilities

### 9.2 Language-Locked Export

Ascension exports are locked to the language of the ingested source code. A developer who uploads Python code exports Python artifacts; a developer who uploads Rust exports Rust artifacts. Cross-language export is not permitted, ensuring the exported code is idiomatic to the developer's stack.

### 9.3 Supported Export Languages

**Software (18):** TypeScript, JavaScript, Python, Rust, Go, Java, C, C++, C#, Ruby, Swift, Kotlin, PHP, Scala, Lua, Dart, Elixir, Haskell

**Hardware Description (7):** Verilog, SystemVerilog, VHDL, Chisel, SpinalHDL, Amaranth, SPICE

### 9.4 IP Protection Mechanisms

| Mechanism | Purpose |
|-----------|---------|
| **Hex-encoded CJPI weights** | Scoring parameters stored as hex arrays (e.g., `[0x1E, 0x1E, 0x14, 0x14]`), not human-readable constants |
| **Comment stripping** | All internal comments removed from exported code |
| **Genericized naming** | Internal variable and function names replaced with non-descriptive identifiers |
| **Sealed discovery heuristics** | The chain archetype registry and synergy matrix are not included in exports |
| **Moat signatures** | Cryptographic UUIDs that tie each capability to its discovery context |
| **Structural fingerprints** | SHA-256 chain fingerprints that detect tampering |

The result: decompiling an Ascension export reveals functional code but provides no insight into the discovery process, scoring methodology, or substrate architecture that produced it.

### 9.5 Portability Guarantee

If CMPSBL ceased to exist, every exported artifact would continue to function. The Mini-Runtime Engine is a standalone execution environment with zero external dependencies. This is the portability guarantee: the export is not a reference to a cloud service but a self-contained software product.

## 14. Hashing and Fingerprinting Implementation

### 14.1 Name Hashing (DJB2 Variant)

The collision engine uses a DJB2-variant hash function for deterministic name-based scoring:

```
function hashString(s: string): number {
    hash = 0
    for each character c in s:
        hash = ((hash << 5) - hash) + charCode(c)
        hash = hash & hash   // Convert to 32-bit integer
    return abs(hash)
}
```

This produces consistent scores for the same input across all executions, ensuring reproducibility.

### 14.2 Structural Fingerprinting (SHA-256)

Discovery fingerprints use the Web Crypto API's SHA-256 implementation:

```
function generateFingerprint(chain: string[], epoch: string): string {
    payload = JSON.stringify({
        steps: chain.map(m => ({ module: m, capability: "collision" })),
        epoch: epoch
    })
    hash = SHA-256(UTF-8(payload))
    return hexEncode(hash)    // 64-character hex string
}
```

The `epoch` parameter ("SPARTA" in the current implementation) allows for versioned fingerprinting — changing the epoch invalidates all prior fingerprints, enabling controlled migration.
