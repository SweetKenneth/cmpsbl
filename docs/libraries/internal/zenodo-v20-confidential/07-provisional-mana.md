## TITLE

SYMBIOTIC ATTACHMENT RUNTIME FOR BINDING GOVERNANCE CONTRACTS TO ARBITRARY SOURCE CODE AT DISTRIBUTION TIME WITH POLYGLOT EMISSION AND TAMPER-EVIDENT INVOCATION RECEIPTS

## FIELD OF THE INVENTION

Runtime governance of distributed software; inline policy attachment; polyglot wrapper emission; tamper-evident receipt chains for code execution.

## BACKGROUND

Existing policy-enforcement systems live at the platform layer (network firewalls, API gateways, container hosts). When code crosses an organizational or environmental boundary, the policy stays behind. Aspect-oriented programming (AOP) frameworks attach behaviors at function boundaries but: (a) modify the host bytecode rather than preserving source verbatim; (b) provide no tamper-evident receipt of invocations; (c) are language-bound, with no polyglot emission of equivalent contracts; (d) lack a discovery counterpart that surfaces which boundaries warrant wrapping. There is no prior method that produces a self-contained artifact in which the original source is byte-perfectly preserved, a governance contract is bound at distribution time, every invocation produces a chained receipt, and the same contract is emitted across multiple programming languages from a single specification.

## SUMMARY

Disclosed is a method comprising: receiving source code; receiving a governance specification expressed as a priority-ordered rule registry hereinafter Lex; producing a wrapper artifact that contains the original source byte-perfect as an inline string literal within the wrapper file; binding the Lex registry to the wrapper such that every invocation of any wrapped function is evaluated against the registry before execution; emitting tamper-evident receipts that chain into a Merkle audit log; supporting controlled detachment of the wrapper while preserving the original source; emitting equivalent wrappers across thirty-four (34) native programming languages and fifty-three (53) bridge environments from a single contract specification.

## DETAILED DESCRIPTION

### Wrapper construction

The wrapper file is generated by an emitter that selects a per-language template, embeds the original source as a verbatim string literal within the template, and inlines the Lex registry as a frozen data structure. A SHA-256 hash of the original source is computed at construction and embedded in the wrapper for runtime verification. The wrapper is self-contained: it has no sibling-file dependency on the original.

### Lex governance

Lex is a priority-ordered rule registry. Each rule contains: `{ id, capability, target, verdict, reason, createdAt, priority }`. Capabilities may be specific (one of 92 named capabilities) or wildcard (`*`). Targets may be specific function names or wildcard. Verdicts are `allow`, `deny`, or `observe`. Priority is a non-negative integer normalized to `[0, 1000]` with lower values indicating higher priority. Ties are broken by `createdAt` (older wins).

Evaluation: at every wrapped invocation, rules are sorted by `(priority asc, createdAt asc)` and traversed. The first rule whose `(capability, target)` matches the invocation returns its verdict. If no rule matches, the verdict defaults to `allow` in `permissive` mode and `deny` in `strict` mode.

### The 92 capabilities and their phases

Mana defines exactly 92 named capabilities, each bound to one of five execution phases:

- **GATE (phase 0)** — denial-on-evaluate before any execution
- **VALIDATE (phase 1)** — input cleaning and threat scoring
- **FAILSAFE (phase 2)** — circuit breaker, timeout, retry
- *(original function executes here)*
- **OBSERVE (phase 3)** — telemetry, audit, metrics
- **ANALYZE (phase 4)** — post-execution inference, anomaly detection

When multiple capabilities are attached to the same function, wrappers are composed in phase order. Within a phase, ordering is alphabetical by capability name for deterministic composition.

### Capability contract table

Every capability has a contract: `{ capability, phase, denySemantic, blocking, lexKey }`. The `denySemantic` is one of `throw | return_undefined | return_message | swallow`, defining what occurs when Lex denies a runtime invocation. The `lexKey` permits multiple capabilities to share a single Lex evaluation key, simplifying rule authoring.

### Receipt chain

Every governed invocation produces a structured telemetry event `{ timestamp, capability, functionName, action, evalContext?, metadata }`. Events are appended to a per-session telemetry log capped at `maxTelemetryEvents` (default 10000). The audit chain (shared with Ascension) appends per-pipeline events with FNV-1a per-entry hashing and periodic SHA-256 anchoring.

### Polyglot emission

A single layer specification is rendered into 34 native language emitters (TypeScript, JavaScript, Python, Go, Rust, Java, C#, C, C++, Ruby, PHP, Swift, Kotlin, Scala, Perl, Lua, Julia, R, Haskell, Erlang, Elixir, OCaml, Clojure, F#, Dart, Crystal, Nim, Zig, V, Bash, PowerShell, SQL, GLSL, Verilog) and 53 bridge environments. The same Lex contract applies regardless of host language.

### Safe detach

The wrapper supports a controlled detach operation that removes Mana while preserving the original source byte-perfect. Detach emits a verification report enumerating every wrapped function, its restoration status, and the SHA-256 verification of the restored source against the construction-time hash.

### Recursive composition

Wrappers may be wrapped. Layer depth is tracked by the engine state (`layerDepth`); the parent layer's hash is recorded as `parentLayerHash`. This enables Mana to wrap Mana — a V3 wrapper around a V2 wrapper around the V1 host — with the receipt chain spanning the entire composition.

## CLAIMS

1. A computer-implemented method for binding governance contracts to arbitrary source code, comprising: receiving source code; receiving a priority-ordered rule registry; producing a wrapper artifact in which the source code appears byte-perfect as an inline embedding; binding the rule registry to the wrapper such that every invocation of any wrapped function is evaluated against the registry before execution; emitting a structured receipt for every governed invocation; appending the receipt to a Merkle-linked audit chain.

2. The method of claim 1, wherein the wrapper artifact contains a SHA-256 hash of the original source computed at construction time, and runtime verification fails if the embedded source does not match the hash.

3. The method of claim 1, wherein the rule registry supports wildcard capabilities and wildcard target function names.

4. The method of claim 1, wherein rule evaluation order is deterministic, sorted by integer priority ascending with ties broken by creation timestamp.

5. The method of claim 1, wherein the wrapper attaches behaviors selected from a fixed set of exactly ninety-two (92) named capabilities.

6. The method of claim 5, wherein each of the 92 capabilities is bound to one of five deterministic execution phases: GATE, VALIDATE, FAILSAFE, OBSERVE, ANALYZE.

7. The method of claim 6, wherein when multiple capabilities are attached to the same function, wrappers compose in phase order with intra-phase ordering alphabetical by capability name.

8. The method of claim 1, wherein the wrapper is emitted in any of thirty-four (34) native programming languages from a single layer specification.

9. The method of claim 1, further comprising a controlled detach operation that removes the wrapper while preserving the original source byte-perfect, with a verification report comparing the restored source against the construction-time SHA-256 hash.

10. The method of claim 1, wherein wrappers may be recursively composed such that a second wrapper governs a first wrapper, with the audit chain spanning the entire composition.

11. The method of claim 1, wherein the receipt for each invocation includes the capability, target function name, action, evaluation context, and the identifier of the rule that produced the verdict.

12. The method of claim 1, wherein the audit chain genesis is a literal string identifier and each entry's hash includes the index, timestamp, action, detail, and previous hash.

13. The method of claim 1, wherein each wrapper carries a frozen copy of the rule registry such that registry mutation in the originating environment does not affect rules embedded in distributed artifacts.

14. The method of claim 1, wherein the verdict for unmatched rules defaults to allow in permissive mode and deny in strict mode.

15. The method of claim 1, wherein each capability has a contract specifying the consequence of a deny verdict from the set `{ throw, return_undefined, return_message, swallow }`.

16. A non-transitory computer-readable medium storing instructions that when executed perform the method of claim 1.

17. A system comprising at least one processor configured to perform the method of claim 1.

18. The method of claim 1, wherein the wrapper is produced without modifying any byte of the original source.

19. The method of claim 1, wherein the same rule registry produces the same verdict for the same `(capability, target)` invocation across independent runs.

20. The method of claim 1, wherein the polyglot emitters share a single contract specification, and a verdict produced by the registry in one host language is structurally equivalent to the verdict produced in any other host language.

## ABSTRACT

A symbiotic attachment runtime that binds governance contracts to arbitrary source code at distribution time. The runtime travels with the wrapped code as a self-contained artifact in which the original source is preserved byte-perfect as an inline embedding. Every invocation of any wrapped function is evaluated against a priority-ordered rule registry (Lex) that supports wildcards, deterministic priority resolution, and a fixed set of ninety-two named capabilities organized into five execution phases. Each governed invocation produces a tamper-evident receipt that chains into a Merkle audit log. Wrappers may be recursively composed, may be safely detached with byte-perfect restoration verified by SHA-256, and are emitted across thirty-four native programming languages from a single contract specification.
