01 Plain English — Why This Matters

Imagine you wrote a piece of software. It works. You're proud of it. Now imagine someone could take that software and make it dramatically more resilient, secure, and intelligent — without changing a single line of your code. Not one character modified. Your original source stays exactly as you wrote it.

That's what the Dual-Layer Architecture does.

Think of it like putting a car into a protective shell. The car still runs the same engine, still has the same interior, still drives the same way. But now it has an armored exterior, an intelligent co-pilot system, self-healing tires, and a black box recording everything that happens. The car itself was never modified — the intelligence was layered around it.

The Core Idea

Layer 1 is your original code — untouched, unmodified, exactly as you wrote it.
Layer 2 is the CMPSBL® Sealed Runtime™ — a protective intelligence shell that wraps around your code, providing resilience, governance, telemetry, and cognitive capabilities without altering the source.

02 What Is the Dual-Layer Architecture?

The Dual-Layer Architecture is the patented core mechanism by which CMPSBL® transforms arbitrary source code into a Sealed Runtime™ — a production-hardened artifact that combines the developer's original code (Layer 1) with an autonomous cognitive infrastructure shell (Layer 2).

Formal Definition

A dual-layer software artifact is a single-file deliverable in which:

  1. Layer 1 (Source Layer) contains the developer's original source code, unmodified, occupying a defined region of the output file.
  2. Layer 2 (Runtime Layer) contains the CMPSBL® Convex Core™ — an obfuscated, self-contained cognitive engine that wraps, monitors, governs, and protects the Source Layer at execution time.

The two layers are merged into a single artifact during the Ascension process. The Runtime Layer intercepts execution entry points, routing all function calls through its governance pipeline before delegating to the original source. The source code is never parsed, rewritten, or transpiled — it is embedded verbatim.

Key Differentiator

Unlike traditional code transformation tools (transpilers, optimizers, bundlers) that modify source code, the Dual-Layer Architecture treats source code as a read-only payload. All intelligence, governance, and resilience are injected as a separate co-resident layer that operates alongside — never inside — the original code.

03 Exactly How It Works — Step by Step

Phase 1: Code Ingestion

The developer uploads or submits their source code to the Ascension pipeline. The code is stored temporarily (never used for training, never shared across tenants) and assigned a Fingerprint ID — a deterministic hash that uniquely identifies this specific submission.

Phase 2: Classification & Analysis

A diagnostic squad of 6 analysis primitives inspects the source code without modifying it:

  • Cyclomatic Complexity Scanner — maps decision branching depth
  • Nesting Depth Analyzer — measures structural complexity
  • Dependency Graph Builder — identifies import/export topology
  • Error Surface Mapper — locates unhandled failure points
  • Security Heuristic Scanner — flags potential vulnerability patterns
  • Pattern Archetype Classifier — categorizes the code's behavioral archetype (Active, Passive, Hybrid)

This produces a Depth Score (0–100) that characterizes the code's structural sophistication.

Phase 3: Primitive Collision

The code's characteristics are "collided" against the 40-Primitive matrix (or 120-candidate pool in Ultimate mode). Each primitive's capabilities are scored against the code using the CJPI (Crown Jewel Performance Index) algorithm with deterministic FNV-1a seeded variance. This produces a ranked list of which primitives are most relevant to this specific codebase.

Phase 4: Capability Selection

Based on collision scores, the engine selects capabilities:

  • Standard Ascension: 20 capabilities (10 Spine + 10 Expansion)
  • Ultimate Ascension: 40 capabilities (unrestricted from 120-candidate pool)

Phase 5: Runtime Assembly

The Convex Core™ is assembled with only the selected primitive handlers activated. Unneeded primitives are excluded to minimize runtime footprint. The runtime is then obfuscated via the WRAITH blackbox engine.

Phase 6: Dual-Layer Merge

The original source code (Layer 1) and the assembled runtime (Layer 2) are merged into a single artifact:

Phase 7: Sealing & Packaging

The merged artifact is sealed with an FNV-1a integrity hash computed over the entire primitive registry. This hash is embedded in the artifact and verified on boot — any tampering triggers an immediate integrity failure. The final package is delivered as a ZIP containing:

  • The sealed single-file artifact (obfuscated)
  • Premium HTML Report (mobile-friendly, word-break: keep-all)
  • Universal User Guide (USER-GUIDE.html)
  • Project meta-files (fingerprint, tier, timestamp)

Phase 8: Runtime Boot Sequence

When the sealed artifact executes:

  1. The Convex Core™ initializes and verifies its own integrity hash
  2. Circuit breaker states are restored from persistence (if available)
  3. Primitive handlers are registered in the execution registry
  4. Telemetry compression engine starts batching events
  5. The original source code executes normally — all calls are transparently intercepted by the runtime's governance pipeline

04 The "Without Source Modification" Guarantee

This is the architectural claim at the heart of the patent. It requires careful understanding because it sounds too good to be true — and yet it's exactly how the system works.

What "No Source Modification" Means

  • The developer's original source code bytes are embedded verbatim in the output artifact
  • No AST (Abstract Syntax Tree) transformation is performed on the source
  • No lines are added, removed, or rewritten inside the source region
  • No variables, functions, or imports in the source are renamed or altered
  • The source code occupies a clearly delineated region that can be extracted and diff'd against the original to confirm zero modifications

What Does Change

  • The execution environment changes. The source code runs inside a governed runtime that intercepts, monitors, and protects execution flows.
  • The artifact wrapper is new. Additional code (the Convex Core™) is prepended/appended around the source region.
  • The entry point may be redirected. Instead of executing the source directly, the runtime boots first and then delegates to the source.
Important Distinction

The claim is "without source modification," not "without any code addition." New code is added — but it's added alongside the source, not inside it. The source region is a read-only payload within the larger artifact. This is analogous to how a ZIP file contains a file without modifying it — the ZIP container is new, but the contained file is byte-identical.

Verifiability

The system provides a verification mechanism: the Fingerprint ID assigned during ingestion can be used to compare the original submission against the source region extracted from the sealed artifact. A byte-for-byte match confirms zero modification. This is critical for:

  • Regulatory compliance (proving code provenance)
  • Enterprise audit trails (no unauthorized modifications)
  • Legal defensibility (patent claims are verifiable)

05 The Convex Core™ — The Engine Inside the Shell

The Convex Core™ (v2.1.0) is the technical core that makes the Dual-Layer Architecture possible. It's a zero-dependency, self-contained JavaScript/TypeScript engine that provides four critical subsystems:

5.1 Telemetry Compression Engine

Every primitive execution generates telemetry events. In a naive implementation, this would create significant overhead. The compression engine uses a bounded 500-entry circular buffer to batch events, achieving approximately 85% reduction in telemetry overhead. 

// Batched telemetry reduces overhead by ~85%
interface CompressedTelemetryBatch {
  batchId: string;
  primitiveId: string;
  eventCount: number;
  firstTs / lastTs: number;
  avgConfidence: number;
  successCount / failureCount: number;
  compressedAt: number;
}

5.2 Circuit Breaker State Persistence

Each primitive handler is protected by an independent circuit breaker. When a handler fails repeatedly (threshold: 3 consecutive failures), the breaker opens and blocks further calls for a cooldown period (default: 30 seconds). Critically, breaker states can be exported and imported across runtime restarts: 

exportCircuitBreakerState(): Record<string, BreakerSnapshot>
importCircuitBreakerState(state: Record<string, BreakerSnapshot>): void

This means if a sealed artifact crashes and restarts, it remembers which primitives were failing and doesn't immediately re-trigger known-bad code paths.

5.3 Timeout Governance

Every primitive handler execution is wrapped in a Promise.race against a 5-second timeout budget. If a handler exceeds this budget, the system returns a gracefully degraded result rather than hanging: 

const result = await Promise.race([
  handler(data, confidence),        // actual execution
  timeoutPromise(5000, primitiveId) // 5s governance budget
]);

Timed-out executions return confidence * 0.3 — a heavily penalized but non-zero result that allows downstream consumers to make informed decisions about data quality.

5.4 Integrity Verification

On boot, the runtime computes an FNV-1a hash of its own primitive registry and compares it against the sealed canonical signature. A mismatch indicates tampering: 

function verifyRuntimeIntegrity(): {
  valid: boolean;
  expected: string;
  actual: string;
  registeredCount: number;
}

This prevents adversaries from injecting malicious handlers into the primitive registry after the artifact has been sealed.

Why the Runtime Is the Key

Architectural Insight

Without the Convex Core™, the Dual-Layer Architecture would be nothing more than code concatenation. The runtime is what transforms a "file with code wrapped around it" into a governed, self-healing, tamper-evident cognitive artifact. It provides the intelligence, the governance, the resilience, and the verification that make the dual-layer concept valuable. Every improvement to the runtime retroactively improves every future sealed artifact.

06 Ultimate Ascension & the Discovery Pipeline

Standard Ascension

Standard Ascension processes code through the 40-Primitive matrix (24 Spine + 16 Expansion) and selects 20 optimal capabilities (10 Spine / 10 Expansion). The process is tier-gated to Architect ($249) and above.

Ultimate Ascension

CMPSBL ULTIMATE™ removes all category restrictions. Instead of the standard 40-Primitive pool, it draws from a 120-candidate ecosystem-wide pool spanning all five industry verticals (Cybersecurity, Robotics, Quantum, LLM, Agency) plus the 16 Universal gap-fill primitives. The scanner dynamically selects all 40 slots based on the highest compounding CJPI scores for the specific codebase.

Extended Collision Protocol

Ultimate Ascension employs a multi-pass scoring approach:

  1. Pass 1 — Signal Density: Each of the 120 candidates is scored against the code's characteristic fingerprint
  2. Pass 2 — Capability Breadth: Candidates with overlapping capabilities are de-duplicated, favoring the higher-scored variant
  3. Pass 3 — Vertical Bonus: Expansion primitives receive a deterministic bonus (+10 to +25, capped at 96) to ensure they compete fairly against core Spine primitives
  4. Pass 4 — Compounding: The final 40 are selected by optimizing for complementary capability coverage — maximizing the total unique capability surface

This extended process takes approximately 217 seconds — compared to ~45 seconds for standard Ascension — because every candidate must be evaluated against every other candidate for compounding effects.

Deterministic Guarantee

A critical property of the Ascension pipeline is determinism. The same input code will always produce the same collision results, the same primitive selections, and the same CJPI scores. This is achieved by replacing all sources of randomness with a seeded FNV-1a PRNG: 

// Seeded variance replaces Math.random()
const seed = fnvSeed(`${primitive.id}::${capability}`);
const variance = 0.7 + deterministicVariance(seed) * 0.3;
const affinity = baseAffinity * variance;

This determinism is essential for the patent claim — it proves the hardening process is reproducible and verifiable, not dependent on random chance.

10 What Could Go Wrong — Failure Mode Analysis

Failure Mode Probability Severity Impact Mitigation
Integrity Hash Mismatch Low Critical Runtime refuses to boot. Artifact is non-functional. Re-export from Ascension pipeline. Verify ZIP integrity during download.
Circuit Breaker Cascade Medium High Multiple primitives trip breakers simultaneously, reducing cognitive coverage. Breakers auto-recover after 30s cooldown. Staggered thresholds prevent cascade.
Timeout Governance False Positive Medium Medium A legitimate long-running handler is terminated early, returning degraded confidence. Increase timeout budget for known-slow primitives. Monitor telemetry for timeout frequency.
Telemetry Buffer Overflow Low Low Oldest telemetry events evicted when buffer exceeds 500 entries. Historical data lost. Flush events before buffer fills. Increase buffer size for high-throughput applications.
Bridge Layer Failure Very Low Critical Source code executes without governance — all runtime protections bypassed. Bridge failure triggers BEACON health alert. Source still functions but ungoverned.
Obfuscation Reversal Low High Adversary reverses WRAITH encoding to extract CJPI weights and proprietary logic. Legal protection (patent, trade secret). Runtime operates correctly even if deobfuscated.
Source-Runtime Version Mismatch Very Low Medium If source is updated externally after sealing, the sealed artifact becomes stale. Re-run Ascension with updated source. Fingerprint ID detects version drift.
Primitive Handler Memory Leak Low Medium A handler accumulates state without release, eventually exhausting runtime memory. Bounded buffers on all handlers. Telemetry tracks memory growth patterns.

11 Troubleshooting Guide

Problem: Sealed artifact won't execute

Symptoms

Artifact fails silently on boot or throws an integrity verification error.

Steps

  1. Check if the ZIP was corrupted during download (re-download and extract again)
  2. Verify the file wasn't modified after extraction (check file size against meta-file)
  3. Run verifyRuntimeIntegrity() manually — if it returns valid: false, the artifact has been tampered with
  4. Re-export from the Ascension pipeline using the same Fingerprint ID

Problem: Circuit breakers keep tripping

Symptoms

Multiple primitives show "open" breaker state. Cognitive coverage is degraded.

Steps

  1. Export breaker state: exportCircuitBreakerState()
  2. Identify which primitives are failing and why (check failCount per handler)
  3. The most common cause is a downstream dependency failure (API timeout, database unavailable) — check the source code's external dependencies
  4. Breakers auto-recover after 30 seconds. If they keep re-tripping, the underlying issue must be resolved in the source code
  5. For emergency recovery, manually reset breaker state: importCircuitBreakerState({})

Problem: Unexpectedly low confidence scores

Symptoms

Handler outputs have confidence values of 0.3 or below when they should be higher.

Steps

  1. Check telemetry for timeout events — a confidence of exactly input × 0.3 indicates timeout governance triggered
  2. Identify which handlers are timing out (exceeding 5s budget)
  3. Profile the handler: is it doing legitimate heavy computation, or is it blocked on I/O?
  4. If legitimate: consider increasing the timeout budget in the runtime config
  5. If blocked: fix the I/O bottleneck in the source code

Problem: Telemetry events missing

Symptoms

Expected telemetry events are not appearing in the batch output.

Steps

  1. Check if the 500-event buffer is overflowing — high-frequency execution may evict old events before they're flushed
  2. Increase flush frequency or buffer size
  3. Verify compression is working: flushTelemetry() returns the current batch
  4. Check if the primitive in question has its breaker open (open breakers don't generate execution telemetry)

Problem: Deterministic scoring producing unexpected results

Symptoms

The same input code produces different primitive selections on re-submission.

Steps

  1. This should never happen if the input is truly identical — the FNV-1a seeded PRNG guarantees determinism
  2. Verify the input file is byte-identical (check Fingerprint ID)
  3. Check if the primitive catalog has been updated between runs (new primitives = different collision results)
  4. If the catalog is identical and the input is identical but results differ, this is a critical bug — escalate immediately

12 Future Roadmap & Improvements

Near-Term (v2.2 — v2.5)

Enhancement Impact Description
Adaptive Timeout Budgets High Instead of a flat 5s budget, learn optimal timeouts per handler based on historical execution telemetry. Handlers that consistently finish in 200ms get 1s budgets; handlers that need 4s get 6s.
Hierarchical Circuit Breakers High Group related primitives under parent breakers. If MEMORY + BRAIN both fail, open a "Cognitive Core" parent breaker that prevents all dependent primitives from executing, reducing cascade noise.
Telemetry Streaming Medium Stream compressed telemetry batches to an external endpoint in real-time, enabling live monitoring of sealed artifacts in production.
Multi-File Artifacts High Extend the Dual-Layer Architecture to handle multi-file codebases (not just single files). The runtime would wrap an entire project structure while maintaining the "no source modification" guarantee across all files.

Mid-Term (v3.0 — v3.5)

Enhancement Impact Description
Language-Agnostic Runtime Critical Port the Convex Core™ from TypeScript/JavaScript to a polyglot runtime that can wrap Python, Go, Rust, and Java codebases. This massively expands the addressable market.
Self-Healing Handlers High When a primitive handler fails, the runtime attempts to automatically repair the input and retry (leveraging the IMMUNE wrapper's repair intelligence) before opening the circuit breaker.
Runtime Hot-Patching High Allow the runtime layer to be updated without re-sealing the entire artifact. The source layer remains untouched; only the runtime receives patches. Requires versioned runtime manifests.
Distributed Dual-Layer Medium For microservice architectures, distribute the runtime across multiple sealed artifacts that communicate via a shared governance bus, maintaining holistic circuit breaker and telemetry state.

Long-Term (v4.0+)

  • Hardware-Level Sealing: Leverage TPM/TEE (Trusted Platform Module / Trusted Execution Environment) to enforce integrity verification at the hardware level, making tampering detection cryptographically unbreakable
  • Autonomous Runtime Evolution: The sealed runtime monitors its own effectiveness and autonomously adjusts primitive weights, timeout budgets, and governance thresholds based on real-world execution patterns — without human intervention
  • Cross-Artifact Learning: Multiple sealed artifacts in the same organization share anonymized telemetry, enabling fleet-wide pattern recognition (e.g., "70% of our artifacts are timing out on MEMORY handlers — investigate infrastructure")
