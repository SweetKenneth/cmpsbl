Written Specification

Unified Software Integrity Lifecycle System Comprising Deterministic Capability Discovery, Non-Intrusive Runtime Attachment with Integrated Governance, and Multi-Signal Behavioral Verification

Field of the Invention

This invention relates to a unified computer-implemented method for managing the integrity and behavioral governance of software functions across their full operational lifecycle. The method encompasses three interdependent phases: (1) deterministic analysis of software to identify functions requiring integrity enhancement; (2) non-intrusive attachment of governance, security, and observability capabilities to identified functions at runtime without modification of the underlying source code; and (3) independent behavioral verification to detect whether functions have been subjected to authorized or unauthorized runtime modification. The three phases are expressions of a single underlying process in which software functions are classified, enhanced, and continuously verified as a closed lifecycle.

Background of the Invention

Modern software is composed of functions authored by distributed parties, imported as dependencies, and executed in runtime environments where their behavior may diverge from the author's intent. Three related problems arise from this reality:

  1. The Discovery Problem: Given an arbitrary body of software source code, how does one deterministically identify which functions require security hardening, governance oversight, or behavioral monitoring — without relying on human judgment or external AI inference?
  2. The Attachment Problem: Once functions requiring enhancement have been identified, how does one attach governance, security, and observability capabilities to those functions at runtime without modifying the original source code, and without the host software's awareness?
  3. The Verification Problem: Once attachment is possible — by authorized or unauthorized parties — how does one independently detect whether a function's runtime behavior has been modified, regardless of the technique used to perform the modification?

These three problems have been addressed independently in prior art: static analysis tools address aspects of discovery; middleware and instrumentation frameworks address aspects of attachment; and integrity verification tools address aspects of detection. However, no prior art unifies all three as a single closed-loop lifecycle in which discovery drives attachment, attachment drives verification, and verification confirms the integrity of both the attachment and the original host.

The inventor has separately filed patent applications addressing the first two phases individually: U.S. App. No. 64/029,678 (discovery and hardening) and U.S. App. No. 64/031,637 (attachment and governance). The present application describes the unified method that connects all three phases into a single process and, in particular, claims the detection/verification methodology (Phase III) and the lifecycle integration that makes all three phases interdependent.

Summary of the Invention

The present invention provides a unified computer-implemented method comprising three interdependent phases that together form a closed software integrity lifecycle:

Phase I — Deterministic Capability Discovery

The system receives as input arbitrary software source code. It applies a deterministic classification process — without external AI inference — to identify function boundaries and classify each function according to its behavioral role. Classification is performed by evaluating source code against a fixed matrix of behavioral primitives. The output of Phase I is a structured map of functions and their assigned capability requirements (e.g., "this function handles state mutation and requires governance oversight; this function processes external input and requires defensive validation").

Phase II — Non-Intrusive Runtime Attachment with Governance

The system receives as input the capability map produced by Phase I and a reference to the host software's runtime module. It attaches the specified capabilities — including but not limited to security gates, behavioral telemetry, governance hooks, circuit breakers, audit trails, and access control rules — to the identified functions at their runtime export boundaries. The attachment is performed such that: (a) the original source code is not modified in any way; (b) the host software's cryptographic hash remains identical before and after attachment; (c) the attached capabilities are governed by a policy engine ("Lex") that evaluates rules in real time to permit, deny, or observe each function invocation; and (d) the attachment supports recursive composition, meaning multiple independent attachment layers may be stacked on the same host function, each with its own governance policy, and each verifiable independently.

Phase III — Multi-Signal Behavioral Verification

The system provides an independent verification capability that determines, with statistical confidence, whether a given function has been subjected to runtime behavioral modification — whether by the authorized attachment described in Phase II, or by an unauthorized third party. Verification is performed by collecting a plurality of behavioral signals from the function under test and comparing the observed signal profile against a known-good baseline. The verification is technique-agnostic: it detects the behavioral consequences of modification regardless of the specific mechanism used to perform the modification.

Lifecycle Integration

The three phases form a closed loop: Phase I identifies what requires protection; Phase II provides the protection; Phase III verifies that protection is functioning correctly and detects any unauthorized modification that occurred outside Phase II's governance. Phase III's verification results may feed back into Phase I as input signals for re-classification, and Phase II's governance engine may consume Phase III's verdicts to dynamically adjust policy (e.g., activating circuit breakers on functions whose verification status has degraded).

Detailed Description of the Unified Method

1. Phase I — Deterministic Discovery Process

The discovery process receives software source code and produces a capability map. The process comprises the following functional steps:

  1. Function Boundary Identification: The system scans the input source code to identify discrete function boundaries — exported functions, class methods, prototype-attached methods, and other callable units that constitute the software's behavioral interface.
  2. Behavioral Classification: Each identified function is evaluated against a fixed matrix of behavioral primitives. Each primitive represents a category of software behavior (e.g., state mutation, external communication, data transformation, error handling, access control). The evaluation produces, for each function, a set of primitive matches with associated confidence scores.
  3. Primitive Collision Analysis: When a function matches multiple behavioral primitives simultaneously, the system performs collision analysis to determine emergent capability requirements. For example, a function that matches both "state mutation" and "external input handling" primitives may yield a composite requirement for both governance oversight and defensive validation. The collision analysis is deterministic — the same inputs always produce the same outputs.
  4. Capability Map Generation: The system produces a structured capability map that associates each function with its required capabilities, the primitives that drove the classification, and a confidence score. This map is the input to Phase II.

The discovery process operates without external AI inference, machine learning models, or network calls. It is a purely algorithmic, deterministic computation over the source code input.

2. Phase II — Non-Intrusive Attachment Process

The attachment process receives a capability map and a runtime module reference, and produces a governed runtime environment. The process comprises the following functional steps:

  1. Source Fingerprinting: Before any attachment occurs, the system computes a cryptographic fingerprint (SHA-256 or equivalent) of the host software's original function implementations. This fingerprint serves as the integrity baseline for Phase III verification.
  2. Governance Policy Evaluation: For each function-capability pair in the capability map, the system consults the governance engine ("Lex") to determine whether the attachment is permitted. Lex evaluates registered rules in insertion order and emits one of three verdicts: allow (capability is attached and active), deny (capability is blocked; function is not modified), or observe (capability is attached in monitoring-only mode, collecting telemetry without altering behavior).
  3. Capability Attachment: For each permitted attachment, the system interposes the specified capability at the function's runtime export boundary. The interposition is performed such that: the original function's behavior is preserved for all inputs that do not trigger governance rules; the original source code bytes are not altered; the host module's cryptographic hash remains identical; and the attachment is transparent to callers who are not specifically testing for it.
  4. Recursive Layer Registration: Each attachment is registered with a layer depth counter and a cryptographic hash of the parent layer. This enables multiple independent parties to attach capabilities to the same function, with each layer independently identifiable and independently removable.
  5. Manifest Generation: The system produces a manifest documenting all attachment points, the governance verdicts that authorized them, the capabilities applied, and the cryptographic proof that the host source was not modified. This manifest is a sealed artifact that can be independently audited.

3. Phase III — Multi-Signal Behavioral Verification Process

The verification process determines whether a function's runtime behavior is consistent with its known-good baseline or has been modified. The process comprises the following functional steps:

  1. Baseline Establishment: During a trusted initialization period, or by importing pre-computed profiles from a trusted authority, the system records the behavioral signal profile of each function under protection. The baseline captures observable behavioral characteristics across multiple independent signal categories.
  2. Signal Collection: During runtime operation, the system collects behavioral signals from protected functions without modifying those functions or interrupting their operation. Signals are collected across a plurality of independent categories, including but not limited to:
    • Execution timing characteristics (invocation latency, duration variance, return timing);
    • Behavioral fingerprint signals (runtime property states, inheritance topology, identity markers);
    • Call path characteristics (invocation depth, frame composition);
    • Output behavioral analysis (type consistency, structural integrity, value patterns);
    • Resource utilization patterns associated with function execution;
    • Error handling and exception propagation behavior.
  3. Anomaly Scoring: For each observation cycle, the system compares the observed signal vector against the stored baseline. Each signal category yields an individual deviation score. Individual scores are combined using a weighted composite formula to produce an overall integrity score. The weights are configurable and may be tuned for specific runtime environments, threat models, or sensitivity requirements.
  4. Verdict Determination: The composite integrity score is evaluated against configurable thresholds to produce one of four verdicts:
    • VERIFIED — behavior is consistent with baseline (unmodified);
    • SUSPICIOUS — deviation detected but below violation threshold;
    • VIOLATED — behavioral modification detected with high confidence;
    • UNKNOWN — insufficient signal data for determination.
  5. Response Orchestration: Upon a VIOLATED or SUSPICIOUS verdict, the system may initiate configurable responses including: alerting operators, logging forensic data, restoring functions to known-good state, activating circuit breakers, generating cryptographic integrity proofs, or feeding the verdict back to Phase I for re-classification and Phase II for dynamic policy adjustment.

4. Technique-Agnostic Detection

A distinguishing feature of Phase III is that it does not detect any specific modification technique. Instead, it detects the behavioral consequences that are common to all runtime modification approaches. Any interposition of additional logic between a function and its callers — regardless of the mechanism used — produces observable behavioral artifacts in one or more signal categories. By monitoring multiple independent signal categories simultaneously, the system achieves robust detection even when individual signal artifacts are deliberately minimized by a sophisticated adversary.

5. Closed-Loop Lifecycle Integration

The three phases integrate into a closed lifecycle through the following feedback mechanisms:

  1. Discovery → Attachment: Phase I's capability map is the direct input to Phase II. Only functions that Phase I has classified receive capabilities from Phase II.
  2. Attachment → Verification: Phase II's source fingerprint and manifest are inputs to Phase III. Phase III can verify both that the authorized attachment was performed correctly and that no unauthorized attachment has occurred.
  3. Verification → Discovery: Phase III's verdicts may be fed back to Phase I as additional classification signals. A function whose verification status has degraded may be reclassified for additional protection.
  4. Verification → Governance: Phase III's verdicts are consumed by Phase II's governance engine (Lex), which may dynamically adjust its policy — for example, activating deny rules on functions that Phase III has flagged as VIOLATED.

This closed-loop integration means the system continuously adapts its protection posture based on real-time integrity signals, without human intervention.

6. Recursive Self-Verification

The verification system (Phase III) is itself subject to integrity verification. The system bootstraps a verification layer during a cryptographically sealed initialization sequence, establishing a trusted baseline for its own components. This prevents an adversary from disabling or modifying the verification system to evade detection.

7. Cross-Environment Portability

While the preferred embodiment targets JavaScript/ECMAScript runtime environments (browsers, Node.js, Deno, Bun, edge runtimes), the unified method is applicable to any runtime environment that supports: (a) programmatic identification of function boundaries; (b) interposition of logic at function export boundaries without source modification; and (c) observation of function behavioral characteristics during execution. Applicable environments include, but are not limited to: Python, Ruby, Java (via reflection), .NET (via interception), Go (via interface wrapping), and compiled environments with dynamic linking capabilities.

8. Cryptographic Proof of Non-Modification

At each phase boundary, the system generates cryptographic proof artifacts:

  1. Pre-attachment proof: SHA-256 hash of the host source before Phase II executes.
  2. Post-attachment proof: SHA-256 hash of the host source after Phase II executes. This hash MUST match the pre-attachment hash, proving that the source code was not modified.
  3. Verification proof: A signed attestation from Phase III documenting the verification verdict, the signal scores that produced it, and the timestamp of verification.

The combination of matching source hashes (proving non-modification of Layer 1) and behavioral verification results (confirming Layer 2 integrity) constitutes a complete integrity proof chain that is independently auditable by any third party.

Informal Claims

Note: Formal claims are not required for a provisional application. These informal claims are included to define the intended scope of protection and assist patent counsel in drafting the non-provisional application. The claims encompass the unified lifecycle method as well as the individual phases and their integration.

Unified Method Claims

1. A computer-implemented method for managing the behavioral integrity of software functions, comprising: (a) deterministically analyzing software source code against a fixed matrix of behavioral primitives to identify function boundaries and classify each function according to capability requirements, producing a capability map; (b) attaching the specified capabilities to the classified functions at their runtime export boundaries without modifying the underlying source code, subject to governance policy evaluation that permits, denies, or observes each attachment; and (c) independently verifying, through multi-signal behavioral analysis, whether each function's runtime behavior is consistent with a known-good baseline or has been subjected to modification.

2. The method of claim 1, wherein the three phases form a closed lifecycle loop in which: the discovery phase produces inputs consumed by the attachment phase; the attachment phase produces integrity baselines and manifests consumed by the verification phase; and the verification phase produces verdicts consumed by both the discovery phase (for reclassification) and the attachment phase (for dynamic governance adjustment).

3. The method of claim 1, wherein the discovery phase operates without external AI inference, machine learning models, or network calls, producing deterministic outputs for identical inputs.

Discovery Phase Claims

4. The method of claim 1, wherein the discovery phase further comprises: performing primitive collision analysis when a function matches multiple behavioral primitives simultaneously, producing emergent composite capability requirements not present in any single primitive match.

Attachment Phase Claims

5. The method of claim 1, wherein the attachment phase further comprises: computing a cryptographic fingerprint of the host software before attachment; performing the attachment such that an identical cryptographic fingerprint is computable after attachment, thereby proving non-modification of the original source code.

6. The method of claim 1, wherein the attachment phase supports recursive composition, such that multiple independent attachment layers may be stacked on the same host function, each with an independent governance policy, layer depth counter, and parent layer hash, and each independently verifiable and removable.

7. The method of claim 1, wherein the governance policy engine evaluates rules in insertion order, emitting allow, deny, or observe verdicts, and wherein observe verdicts cause the capability to collect telemetry without altering the function's input-output behavior.

Verification Phase Claims

8. The method of claim 1, wherein the verification phase detects behavioral modification in a technique-agnostic manner by observing behavioral consequences common to all runtime modification approaches, without requiring knowledge of the specific modification technique employed.

9. The method of claim 1, wherein the verification phase collects behavioral signals across at least three independent signal categories — selected from execution timing, behavioral fingerprinting, call path analysis, output analysis, resource utilization, and error propagation — and combines individual deviation scores using a weighted composite formula to produce an overall integrity score.

10. The method of claim 1, wherein the verification phase further comprises recursive self-verification, wherein the verification system verifies its own behavioral integrity using a bootstrapped verification layer established during a cryptographically sealed initialization sequence.

System and Medium Claims

11. A system for unified software integrity lifecycle management, comprising: a discovery engine configured to deterministically classify software functions against a primitive matrix and produce capability maps; an attachment engine configured to interpose capabilities at function runtime boundaries without source modification, subject to a governance policy engine; and a verification engine configured to detect runtime behavioral modification through multi-signal anomaly analysis, the three engines integrated in a closed feedback loop.

12. A non-transitory computer-readable medium storing instructions that, when executed by a processor, cause the processor to perform the method of claim 1.

13. The method of claim 1, wherein the method operates across heterogeneous runtime environments including JavaScript, Python, Ruby, Java, .NET, and Go environments.

14. The method of claim 1, wherein the attachment phase generates a sealed manifest artifact documenting all attachment points, governance verdicts, capabilities applied, layer depths, and cryptographic non-modification proofs, the manifest being independently auditable by third parties.
