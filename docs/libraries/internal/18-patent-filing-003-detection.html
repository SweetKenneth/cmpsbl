Written Specification

Runtime Integrity Verification System for Detecting Unauthorized Behavioral Modification of Software Functions Through Multi-Signal Anomaly Analysis

Field of the Invention

This invention relates generally to runtime software security and integrity verification, and more particularly to a system and method for detecting unauthorized behavioral modifications to software functions — including but not limited to runtime wrapping, function interception, middleware injection, prototype chain manipulation, and capability attachment — through multi-signal anomaly analysis conducted without access to or modification of the original source code.

Background of the Invention

Modern software architectures are increasingly exposed to runtime modification techniques that alter the behavior of existing functions without changing the underlying source code. These techniques include, but are not limited to:

  • Function wrapping — replacing a function reference with a wrapper that intercepts calls, modifies arguments, alters return values, or introduces side effects;
  • Prototype chain manipulation — modifying the prototype inheritance chain of objects to inject or override methods;
  • Middleware injection — inserting processing layers between function calls and their consumers;
  • Silent capability attachment — adding governance, telemetry, security, or monetization logic to existing functions at runtime boundaries without developer awareness or consent.

The inventor has separately filed patent applications (U.S. App. Nos. 64/029,678 and 64/031,637) describing systems for performing such attachment and modification. The present invention addresses the complementary problem: detecting when such modification has occurred, regardless of the technique used, and providing a verification signal that software is operating in its original, unmodified state.

Existing integrity verification approaches (checksum comparison, static analysis, code signing) fail to detect runtime modifications because the source code and compiled artifacts remain byte-for-byte identical. The modification occurs entirely in the runtime execution environment, below the visibility of traditional security tools.

There is therefore a need for a runtime integrity verification system that can detect behavioral modification of software functions without requiring access to source code, without modifying the functions under test, and without prior knowledge of the specific modification technique employed.

Summary of the Invention

The present invention provides a runtime integrity verification system comprising a multi-signal anomaly analysis engine that observes the behavioral characteristics of software functions during execution and determines, with statistical confidence, whether those functions have been subjected to unauthorized modification.

The system operates by collecting a plurality of behavioral signals from functions under test and comparing observed signal profiles against baseline behavioral models. Deviations exceeding configurable confidence thresholds trigger integrity violation alerts.

The system is technique-agnostic — it does not look for any specific modification method, but instead detects the behavioral consequences of modification regardless of the underlying mechanism. This makes the system effective against known techniques (wrapping, proxying, prototype manipulation) and unknown future techniques that produce similar behavioral artifacts.

Detailed Description of Preferred Embodiments

1. System Architecture

The runtime integrity verification system comprises the following components:

  1. Signal Collection Module — a non-invasive observer that instruments function execution without modifying the functions under test. The Signal Collection Module gathers behavioral telemetry including but not limited to:
    • Execution timing characteristics (invocation latency, return timing, execution duration variance);
    • Behavioral fingerprint signals (property descriptor states, prototype chain topology, constructor identity, object property enumeration characteristics);
    • Call stack characteristics (depth, frame composition, caller chain topology);
    • Return value behavioral analysis (type consistency, structural integrity, value mutation patterns);
    • Memory and resource utilization patterns associated with function execution;
    • Error handling and exception propagation behavior.
  2. Baseline Model Engine — constructs behavioral profiles for functions in their known-good unmodified state. Baselines may be established through:
    • Initial calibration during a trusted execution period;
    • Importation of pre-computed baseline profiles from a trusted authority;
    • Statistical modeling derived from behavioral invariants common to unmodified functions in a given runtime environment.
  3. Anomaly Analysis Engine — compares observed behavioral signals against baseline models using a weighted multi-signal scoring algorithm. Each signal category contributes to a composite integrity score. The scoring weights are configurable and may be tuned for specific runtime environments, threat models, or sensitivity requirements.
  4. Verdict Engine — consumes composite integrity scores and emits one of the following determinations:
    • VERIFIED — function behavior is consistent with baseline (unmodified);
    • SUSPICIOUS — deviation detected but below violation threshold;
    • VIOLATED — behavioral modification detected with high confidence;
    • UNKNOWN — insufficient signal data for determination.
  5. Response Orchestrator — upon detection of a VIOLATED verdict, the system may initiate configurable defensive responses including but not limited to:
    • Alerting human operators or automated monitoring systems;
    • Logging forensic data for post-incident analysis;
    • Initiating function restoration from known-good state;
    • Activating circuit breakers to isolate compromised functions;
    • Generating cryptographic integrity proofs for audit chains.

2. Multi-Signal Anomaly Analysis Method

The method of detecting unauthorized behavioral modification comprises the following steps:

  1. Establish Baseline: During a trusted initialization period, the system observes each function under protection and records its behavioral signal profile across all signal categories. This profile constitutes the function's behavioral fingerprint.
  2. Continuous Observation: During runtime operation, the Signal Collection Module continuously or periodically samples the behavioral signals of protected functions without interrupting their normal operation.
  3. Signal Comparison: For each observation cycle, the Anomaly Analysis Engine compares the observed signal vector against the stored baseline vector. Each signal category yields an individual deviation score.
  4. Weighted Composite Scoring: Individual deviation scores are combined using a configurable weighted formula to produce a composite integrity score. The weights reflect the relative diagnostic value of each signal category for the specific runtime environment.
  5. Threshold Evaluation: The composite integrity score is evaluated against configurable thresholds to determine the integrity verdict (VERIFIED, SUSPICIOUS, VIOLATED, or UNKNOWN).
  6. Response Execution: Based on the verdict, the Response Orchestrator initiates the appropriate defensive response as configured by the system operator.

3. Signal Categories and Their Diagnostic Value

The invention recognizes that different categories of behavioral signals have different diagnostic value for detecting different types of runtime modification. The following signal categories are identified as having particular diagnostic value:

3a. Property Descriptor Signals

Unmodified functions in JavaScript-compatible runtime environments exhibit specific property descriptor characteristics (configurability, writability, enumerability) that are altered when functions are replaced by wrapper constructs. The system observes these descriptor states as a high-weight integrity signal.

3b. Timing Differential Signals

Runtime modification techniques that interpose additional logic between caller and callee introduce measurable timing overhead. The system establishes baseline execution timing and detects statistically significant deviations. Timing signals are weighted to account for normal variance due to system load, garbage collection, and other non-adversarial factors.

3c. Prototype Chain Topology Signals

Functions in object-oriented runtime environments possess prototype chains that are structurally altered by certain modification techniques. The system maps and monitors prototype chain topology as an integrity signal.

3d. Constructor Identity Signals

Modified functions may exhibit altered constructor references, changed name properties, or inconsistent toString() representations. The system monitors these identity markers as supporting integrity signals.

3e. Call Stack Composition Signals

Wrapper functions and middleware layers introduce additional call stack frames. The system monitors call stack depth and frame composition during function execution as a supplementary integrity signal.

3f. Error Propagation Signals

Modified functions may exhibit altered error handling behavior — swallowing exceptions, wrapping errors in additional context, or modifying error types. The system monitors error propagation patterns as a supplementary integrity signal.

4. Technique-Agnostic Detection

A key feature of the invention is its technique-agnostic nature. Rather than detecting specific modification mechanisms (which would create an arms race requiring constant updates), the system detects the behavioral consequences common to all runtime modification approaches. Any technique that interposes logic between a function and its callers will produce observable behavioral artifacts in one or more signal categories. By monitoring multiple independent signal categories simultaneously, the system achieves robust detection even when individual signals are deliberately minimized by a sophisticated adversary.

5. Recursive Verification

The system supports recursive verification — the ability to verify the integrity of the verification system itself. The Signal Collection Module, Anomaly Analysis Engine, and Verdict Engine are themselves subject to integrity verification by a bootstrapped verification layer that establishes its own trusted baseline during a cryptographically sealed initialization sequence.

6. Cross-Environment Portability

While the preferred embodiment targets JavaScript/ECMAScript runtime environments (browsers, Node.js, Deno, Bun), the multi-signal anomaly analysis methodology is applicable to any runtime environment that supports function-level behavioral observation, including but not limited to: Python, Ruby, Java (via reflection), .NET (via interception), and compiled environments with dynamic linking capabilities.

Informal Claims

Note: Formal claims are not required for a provisional application. These informal claims are included to define the intended scope of protection and assist patent counsel in drafting the non-provisional application.

1. A computer-implemented method for detecting unauthorized runtime modification of software functions, comprising: establishing a behavioral baseline for one or more software functions during a trusted execution period; continuously or periodically collecting a plurality of behavioral signals from the functions during runtime operation; comparing the collected behavioral signals against the stored baseline using a weighted multi-signal scoring algorithm to produce a composite integrity score; and determining, based on the composite integrity score and configurable thresholds, whether the function has been subjected to unauthorized behavioral modification.

2. The method of claim 1, wherein the behavioral signals comprise two or more of: property descriptor state analysis, execution timing differential analysis, prototype chain topology mapping, constructor identity verification, call stack composition analysis, and error propagation pattern analysis.

3. The method of claim 1, wherein the detection is technique-agnostic, detecting behavioral consequences of modification without requiring knowledge of the specific modification technique employed.

4. The method of claim 1, further comprising initiating one or more configurable defensive responses upon detection of unauthorized modification, including alerting, logging, function restoration, circuit breaker activation, or cryptographic proof generation.

5. The method of claim 1, further comprising recursive self-verification, wherein the integrity verification system verifies its own behavioral integrity using a bootstrapped verification layer established during a cryptographically sealed initialization sequence.

6. A system for runtime integrity verification of software functions, comprising: a signal collection module configured to observe behavioral characteristics of software functions without modifying the functions under test; a baseline model engine configured to store behavioral fingerprints of functions in their unmodified state; an anomaly analysis engine configured to compare observed behavioral signals against stored baselines and produce composite integrity scores; and a verdict engine configured to emit integrity determinations based on composite scores and configurable thresholds.

7. The system of claim 6, wherein the signal collection module collects signals across at least three independent signal categories to achieve robust detection even when individual signals are deliberately minimized by an adversary.

8. The system of claim 6, wherein the anomaly analysis engine uses configurable signal weights that may be tuned for specific runtime environments, threat models, or sensitivity requirements.

9. A non-transitory computer-readable medium storing instructions that, when executed by a processor, cause the processor to perform the method of claim 1.

10. The method of claim 1, wherein the method operates across heterogeneous runtime environments including JavaScript, Python, Ruby, Java, and .NET environments.
