## 2. The 40-Primitive Matrix

Every substrate — primary and vertical — runs exactly **40 primitives** organized in a symmetric **12·12·8·8** matrix across 4 categories:

```
┌─────────────────────────────────────────────┐
│              40-PRIMITIVE MATRIX             │
├─────────────────────────────────────────────┤
│  12 ORGANS   — The Body (identity, memory,  │
│                routing, health)              │
│  12 LAYERS   — The Rules (security,         │
│                governance, integration)      │
│  8  ENGINES  — The Workers (discovery,      │
│                synthesis, translation)       │
│  8  AGENTS   — The Specialists (encoding,   │
│                auditing, operations)         │
└─────────────────────────────────────────────┘
```

**Invariant:** Organs and Layers are NEVER changed. They are the **Spine** — the governance and identity backbone shared by every substrate. Engines and Agents are **hot-swappable** — replaced with domain-specific primitives per vertical.

### 3.3 How Organs & Layers Work

**Organs are observable, not interactive.** You can see their health, read their telemetry, but you cannot directly invoke their internals. They are the substrate's vital organs — always running, always monitored.

**Layers enforce rules passively.** DEFENSE doesn't wait for a command to check threats — it wraps every request. GOVERNANCE doesn't wait to be asked — every mutation passes through it. AUDIT doesn't wait to be triggered — every event is logged.

**Execution model:**
```
User Action / System Trigger
    ↓
broadcastIntent()          ← All execution starts here
    ↓
INTENT Router              ← Determines which resolvers to invoke
    ↓
Resolver Execution          ← primitive.resolver_name format
    ↓
Response Aggregation
    ↓
Mesh Communication Events   ← Telemetry (non-blocking)
    ↓
Dashboards / Memory
```

**Key rules:**
- Primitives NEVER call each other directly — only through resolvers via the intent mesh
- Resolver naming: `primitive.resolver_name` (e.g., `brain.reasoning_context`)
- Telemetry is always non-blocking: `logReceipt(...).catch(() => {})`

## 4. The Expansion Surface — Engines & Agents

The 16 expansion slots (8 Engines + 8 Agents) are where verticals differentiate. In the primary substrate, these run the default cognitive primitives (CORTEX, NEXUS, FORGE, etc.). In verticals, they are hot-swapped for domain-specific primitives.

**Primary substrate defaults (for reference):**

| Engines | Agents |
|---------|--------|
| DREAM, HARVEST, FORGE, LINGUA | ENCODE, DECODE, AUDIT, ECONOMY |
| ECHO, PHANTOM, SANDBOX, RIPPLE | INCLUSIVE, CORTEX, ORACLE, ENGINEER |

When a vertical is instantiated, the `assembleVerticalPrimitives()` function merges:
- 24 spine primitives (always inherited)
- Up to 8 custom engines (replacing defaults)
- Up to 8 custom agents (replacing defaults)

**Validation enforced at assembly:**
- Exactly 12 organs, 12 layers, 1–8 engines, 1–8 agents
- All organs and layers must be `inherited: true`
- Primitive weights must sum to 1.000
- Subdomain must be lowercase alphanumeric

## 12. Constant Learning Mode (CLM)

### 12.1 What It Is

The CLM is the substrate's continuous self-improvement engine. It runs autonomous learning cycles that strengthen primitive health scores by ingesting domain-specific curriculum topics.

### 12.2 Architecture

```
CLM Cycle
    ↓
Select batch of primitives (batch size: 4-6)
    ↓
Prioritize degraded primitives (health < 70)
    ↓
For each primitive: real AI call via NEXUS free-tier router
    ↓
Ingest learning → update health score
    ↓
Debounced state persistence → vertical_clm_cycles table
    ↓
Auto-prune old cycles
```

### 12.3 Primary vs. Vertical CLM

| Parameter | Primary | Per Vertical |
|-----------|---------|-------------|
| Cycles/day | 14,400 | 2,400 |
| Batch size | 6 | 4 |
| Curriculum | 40-primitive general | Domain-specific (10 topics) |
| Priority targets | Health < 70 | Vertical-specific (e.g., WATCHTOWER, SERVO) |
| AI routing | NEXUS free-tier | NEXUS free-tier (shared) |
| Schedule | `cdm-primary-substrate` every 8h | `vertical-autonomous-cycle` every 4h |

### 12.4 CLM Isolation

Each vertical's CLM runs independently with its own:
- Curriculum topics (defined in `VerticalCLMConfig`)
- Priority primitive list
- Cycle history (`vertical_clm_cycles` table, scoped by `vertical_id`)
- Health scores (computed per vertical's weighted formula)

**Cross-pollination:** CLM cycles can read from the global Memory Stream pool, meaning insights discovered in one vertical may influence learning in another — but the learning pass itself is always scoped.

## 19. Health, Healing & Circuit Breakers

### 19.1 Health Calculation

Every substrate (primary and vertical) computes health as a weighted sum:

```
Health = Σ(primitive_weight × primitive_health) / Σ(primitive_weight)
```

Each primitive has a health score (0–100). Healthy range: **≥ 80**.

Detailed health formula includes:
- Query Latency (25%)
- Data Presence (15%)
- Recent Activity (20%)
- Module-Specific Diagnostics (40%)

### 19.2 Circuit Breakers

**Every primitive has its own circuit breaker.** If a primitive fails:

1. Circuit breaker trips → primitive marked degraded
2. System continues operating at reduced capability
3. MEDIC layer initiates recovery protocol
4. IMMUNITY detects anomaly pattern
5. After recovery → breaker resets → state reconciliation → audit verification

### 19.3 Zone Shielding

Expansion zones have independent circuit breakers. If an entire zone fails, core operations continue:

| Zone | Impact If Down |
|------|---------------|
| All 8 Engines | Reduced processing, spine intact |
| All 8 Agents | Reduced specialization, spine intact |
| Single primitive | Minimal — other primitives compensate |

### 19.4 The 4 Requirements (Every Component)

Before any component ships, it MUST have:

1. ✅ **Circuit breaker** — Independent failure isolation
2. ✅ **DEFENSE Layer shield** — Security boundary enforced
3. ✅ **Graceful degradation** — Partial function under failure
4. ✅ **BEACON health signal** — Continuous health reporting

### 19.5 Self-Healing Pipeline

```
Anomaly Detected (IMMUNITY)
    ↓
Diagnosis (MEDIC triage)
    ↓
Repair Cycle in Shadow Mode
    ↓
Governed Promotion Pipeline:
    Shadow → Simulation → Preflight → Canary
    ↓
Governance Approval
    ↓
Production Application
    ↓
AUDIT logged
```

### 19.6 SEBA (Self-Evolving Behavioral Architecture)

For deeper issues, the SEBA 7-gate pipeline handles self-improvement:

```
Candidate → Lint → Test → Security → Blast Radius →
Evidence → Governance → Production
```

**ENCODE writes patches.** Every rejection hardens the learning curriculum.

### 19.7 Healing Across Verticals

To heal the entire ecosystem:

1. **Check primary health first** — spine health affects all verticals
2. **Run CLM priority pass** — degraded primitives (< 70 health) get extra cycles
3. **Check per-vertical health** — each vertical's `calculateVerticalHealth()` reports independently
4. **MEDIC handles recovery** — inherited spine MEDIC works across all verticals
5. **Circuit breaker reset** — per-primitive, not per-substrate

**If CORE fails = full system halt.** All other primitives degrade gracefully.

## 24. Troubleshooting & Recovery

### 24.1 Full Ecosystem Health Check

```
1. Check primary substrate health (weighted sum of 40 primitives)
2. For each vertical: check calculateVerticalHealth()
3. Identify any primitive with health < 70
4. Check circuit breaker states
5. Review AUDIT trail for anomalies
6. Verify CLM cycles are running (check vertical_clm_cycles timestamps)
7. Verify Memory Stream deposits are flowing (check vertical_memory_stream)
8. Confirm pg_cron jobs are active
```

### 24.2 Common Issues

| Symptom | Cause | Fix |
|---------|-------|-----|
| Vertical health < 80 | CLM not running | Check pg_cron job, verify edge function deployed |
| No new discoveries | CDM cycle failed | Check edge function logs, verify NEXUS router has capacity |
| Memory Stream empty | Cycle interval not elapsed | Wait 4h or trigger manual cycle |
| Spine primitive degraded | Affects ALL verticals | Priority CLM pass on degraded primitive |
| NEXUS 500 errors | Provider exhaustion (TPD/TPM) | Self-throttles automatically; wait for limit reset |
| Crown Jewels not showing | Registry not imported | Verify registry file exports and imports in index.ts |

### 24.3 Nuclear Recovery

If the entire ecosystem needs reset:

1. **CORE boot sequence** — reinitializes all 40 primitives in dependency order
2. **CLM priority pass** — focus on health < 70 primitives
3. **Memory Stream re-seed** — trigger manual deposits for each vertical
4. **Circuit breaker reset** — `resetProviderHealth()` across fleet
5. **AUDIT verification** — confirm tamper-evident chain integrity
6. **One-click backup** captures entire system state for disaster recovery

### 24.4 State Transitions

| State | Description | Recovery Path |
|-------|-------------|--------------|
| **Boot** | CORE initializes → layers cascade → 40 primitives online | Automatic |
| **Steady State** | Processing, monitoring, periodic persistence | Normal |
| **Degraded** | Circuit breaker open on 1+ primitives | CLM priority + MEDIC |
| **Zone Isolated** | Entire expansion zone offline; core continues | Zone-level reset |
