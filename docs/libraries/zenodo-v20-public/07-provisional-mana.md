**Public summary.** Mirrors the structure of the filed provisional held by counsel.

## TITLE

Symbiotic attachment runtime for binding governance contracts to arbitrary source code at distribution time with polyglot emission and tamper-evident invocation receipts.

## FIELD

Runtime governance of distributed software; inline policy attachment; polyglot wrapper emission; tamper-evident receipt chains for code execution.

## BACKGROUND

Existing policy-enforcement systems live at the platform layer (network firewalls, API gateways, container hosts). When code crosses an organizational boundary, the policy stays behind. Aspect-oriented programming (AOP) frameworks attach behaviors at function boundaries but: (a) modify the host bytecode rather than preserving source verbatim; (b) provide no tamper-evident receipt of invocations; (c) are language-bound, with no polyglot emission of equivalent contracts; (d) lack a discovery counterpart that surfaces which boundaries warrant wrapping.

## SUMMARY

Disclosed is a method comprising: receiving source code; receiving a governance specification expressed as a priority-ordered rule registry hereinafter Lex; producing a wrapper artifact that contains the original source byte-perfect as an inline embedding within the wrapper file; binding the Lex registry to the wrapper such that every invocation of any wrapped function is evaluated against the registry before execution; emitting tamper-evident receipts that chain into a Merkle audit log; supporting controlled detachment of the wrapper while preserving the original source; emitting equivalent wrappers across multiple host programming languages from a single contract specification.

## DETAILED DESCRIPTION (overview)

The wrapper file is generated by an emitter that selects a per-language template, embeds the original source as a verbatim inline embedding, and binds the Lex registry as a frozen data structure. A cryptographic hash of the original source is computed at construction and embedded in the wrapper for runtime verification.

**Lex** is a priority-ordered rule registry. Each rule has `{ id, capability, target, verdict, reason, createdAt, priority }`. Capabilities and targets may be wildcard. Verdicts are `allow`, `deny`, or `observe`. Priority is a non-negative integer; lower values indicate higher priority. Ties are broken by `createdAt` (older wins). When no rule matches, verdict defaults to `allow` in `permissive` mode and `deny` in `strict` mode.

Mana defines exactly **92 named capabilities**, each bound to one of five execution phases: **GATE (0)** denial-on-evaluate; **VALIDATE (1)** input cleaning; **FAILSAFE (2)** circuit-breaker / retry / timeout; the original function executes here; **OBSERVE (3)** telemetry; **ANALYZE (4)** post-execution inference. When multiple capabilities attach to the same function, wrappers compose in phase order with deterministic intra-phase tiebreak.

Each capability has a contract specifying the consequence of a deny verdict (throw / return undefined / return message / swallow). The full per-capability contract table is held internally.

The **receipt chain** is shared with Ascension and uses dual-hash construction. The wrapper supports a controlled **detach** that restores the original source byte-perfect with a verification report.

## CLAIMS (twenty)

1. A computer-implemented method for binding governance contracts to arbitrary source code, comprising: receiving source code; receiving a priority-ordered rule registry; producing a wrapper artifact in which the source code appears byte-perfect as an inline embedding; binding the rule registry to the wrapper such that every invocation of any wrapped function is evaluated against the registry before execution; emitting a structured receipt for every governed invocation; appending the receipt to a Merkle-linked audit chain.

2. The method of claim 1, wherein the wrapper artifact contains a cryptographic hash of the original source computed at construction time, and runtime verification fails if the embedded source does not match the hash.

3. The method of claim 1, wherein the rule registry supports wildcard capabilities and wildcard target function names.

4. The method of claim 1, wherein rule evaluation order is deterministic, sorted by integer priority ascending with ties broken by creation timestamp.

5. The method of claim 1, wherein the wrapper attaches behaviors selected from a fixed set of exactly ninety-two (92) named capabilities.

6. The method of claim 5, wherein each of the 92 capabilities is bound to one of five deterministic execution phases: GATE, VALIDATE, FAILSAFE, OBSERVE, ANALYZE.

7. The method of claim 6, wherein when multiple capabilities are attached to the same function, wrappers compose in phase order with deterministic intra-phase tiebreak.

8. The method of claim 1, wherein the wrapper is emitted in any of multiple host programming languages from a single layer specification.

9. The method of claim 1, further comprising a controlled detach operation that removes the wrapper while preserving the original source byte-perfect, with a verification report comparing the restored source against the construction-time hash.

10. The method of claim 1, wherein wrappers may be recursively composed such that a second wrapper governs a first wrapper, with the audit chain spanning the entire composition.

11. The method of claim 1, wherein the receipt for each invocation includes the capability, target function name, action, evaluation context, and the identifier of the rule that produced the verdict.

12. The method of claim 1, wherein the audit chain genesis is a literal string identifier and each entry's hash includes the index, timestamp, action, detail, and previous hash.

13. The method of claim 1, wherein each wrapper carries a frozen copy of the rule registry such that registry mutation in the originating environment does not affect rules embedded in distributed artifacts.

14. The method of claim 1, wherein the verdict for unmatched rules defaults to allow in permissive mode and deny in strict mode.

15. The method of claim 1, wherein each capability has a contract specifying the consequence of a deny verdict from a fixed set of deny semantics.

16. A non-transitory computer-readable medium storing instructions that when executed perform the method of claim 1.

17. A system comprising at least one processor configured to perform the method of claim 1.

18. The method of claim 1, wherein the wrapper is produced without modifying any byte of the original source.

19. The method of claim 1, wherein the same rule registry produces the same verdict for the same capability and target across independent runs.

20. The method of claim 1, wherein the polyglot emitters share a single contract specification, and a verdict produced by the registry in one host language is structurally equivalent to the verdict produced in any other host language.

## ABSTRACT

A symbiotic attachment runtime that binds governance contracts to arbitrary source code at distribution time. The runtime travels with the wrapped code as a self-contained artifact in which the original source is preserved byte-perfect as an inline embedding. Every invocation of any wrapped function is evaluated against a priority-ordered rule registry that supports wildcards, deterministic priority resolution, and a fixed set of ninety-two named capabilities organized into five execution phases. Each governed invocation produces a tamper-evident receipt that chains into a Merkle audit log. Wrappers may be recursively composed, may be safely detached with byte-perfect restoration, and are emitted across multiple host programming languages from a single contract specification.
