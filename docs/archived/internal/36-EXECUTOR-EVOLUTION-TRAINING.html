1. Lifecycle Overview: How an Executor Trains

Every executor begins at Tier 1 (Foundational) with zero history. Training is not a passive process — it is a structured loop that runs on every mutation attempt:

┌─────────────────────────────────────────────────────────────────┐
│  EXECUTOR TRAINING LIFECYCLE (per mutation)                     │
│                                                                 │
│  ① Warm-Up Sequence         → Readiness verification            │
│  ② Complexity Scoring       → Pre-execution risk assessment     │
│  ③ Tier Gate Check          → Is this mutation allowed?         │
│  ④ Micro-Feedback Session   → Step-by-step signal capture       │
│  ⑤ Outcome Recording        → Success/failure to difficulty     │
│                              ladder + repair effectiveness      │
│  ⑥ Failure Classification   → If failed: taxonomy + post-mortem │
│  ⑦ Gap Capture              → If failed: snapshot for replay    │
│  ⑧ Skill Decay Check        → Periodic sliding-window analysis  │
│  ⑨ Calibration Recording    → Confidence vs. reality tracking   │
│  ⑩ Stamina Checkpoint       → Fatigue detection mid-session     │
│  ⑪ Specialty Tree Update    → Domain mastery progression        │
│  ⑫ Pattern Library Ref      → Record which patterns applied     │
│  ⑬ Promotion Check          → Eligible for next tier?           │
│                                                                 │
│  LOOP BACK → Next mutation                                      │
└─────────────────────────────────────────────────────────────────┘

This is not sequential in the strict sense — some steps are conditional (e.g., ⑥–⑦ only fire on failure), and ⑧ runs on a window basis rather than per-mutation. But every mutation touches steps ①–⑤ and ⑨–⑬.

2. The Difficulty Ladder: How Executors Level Up

2.1 Tier Structure

The ladder has 5 tiers. Each tier is a hard gate — the executor physically cannot attempt mutations above their tier's allowances. This is enforced by isMutationAllowed() which checks three dimensions before every mutation:

Tier Level Allowed Mutation Types Max Modules Affected Max Risk Score Promotion Threshold Min Attempts
Foundational 1 prompt_optimization 1 0.15 90% success 20
Intermediate 2 + routing_adjustment, memory_strategy 3 0.30 85% success 30
Advanced 3 + defense_rule 6 0.45 80% success 40
Expert 4 + pipeline_restructure 12 0.55 80% success 50
Master 5 + module_configuration 24 0.60 85% (maintenance) 100

2.2 What Each Tier Unlocks — Ability by Ability

Tier 1 — Foundational

Abilities unlocked:
  • Prompt optimization — Modify system prompts for quality improvement. Single-field repairs only.
  • Null coercion — Handle null/undefined inputs via deterministic repair.
  • Type casting — Convert mismatched types (string→number, etc.).
Constraints: 1 module max. Risk score must stay below 0.15. No routing, no DEFENSE, no MEMORY mutations.

Purpose: Prove the executor can handle the simplest, safest mutations without breaking anything. Zero production impact. If you can't get 90% success on single-field prompt tweaks, you aren't ready for anything else.

Tier 2 — Intermediate

New abilities unlocked:
  • Routing adjustment — Modify provider weights, failover priorities, and latency-based routing rules.
  • MEMORY strategy — Adjust context window sizes, decay rates, and retention policies.
  • Multi-field repair — Repair inputs with 2–3 broken fields simultaneously.
Expanded scope: Up to 3 modules. Risk ceiling raised to 0.30.

Purpose: The executor now touches systems that affect latency and context quality. These are not cosmetic — bad routing causes outages, bad MEMORY config causes hallucination. The 85% threshold at 30 attempts proves consistency under moderate complexity.

Tier 3 — Advanced

New abilities unlocked:
  • DEFENSE rule creation — Create, modify, and delete threat detection rules.
  • Multi-module coordination — Mutations that span 4–6 modules with dependency awareness.
  • Regression-aware mutations — Must demonstrate ability to detect and respond to regressions caused by own mutations.
Expanded scope: Up to 6 modules. Risk ceiling at 0.45.

Purpose: DEFENSE rules are security-critical. A bad rule blocks legitimate traffic; a missing rule lets threats through. The executor must prove they understand cause-and-effect across multiple modules before touching security surfaces.

Tier 4 — Expert

New abilities unlocked:
  • Pipeline restructuring — Reorganize the order, dependencies, and configuration of processing pipelines.
  • Cross-module evolution — Coordinated mutations across up to 12 modules in a single operation.
  • Rollback-critical operations — Mutations where failure requires immediate full-state rollback.
Expanded scope: Up to 12 modules. Risk ceiling at 0.55.

Purpose: Pipeline restructuring can break the entire execution flow. This tier exists because some mutations are inherently dangerous — the executor must have 50+ successful attempts at Advanced tier before being trusted with architectural changes.

Tier 5 — Master

New abilities unlocked:
  • Module configuration — Full configuration access to any module (BRAIN, DECODE, DEFENSE, MEMORY, etc.).
  • Full-scope mutations — Up to 24 modules affected in a single operation.
  • Unrestricted within governance — Only governance rules (budget caps, approval gates) constrain the executor.
Expanded scope: Up to 24 modules. Risk ceiling at 0.60. Still bounded by governance.

Purpose: Master tier requires 100 minimum attempts — this is intentionally high. At this level, the executor can reconfigure any module in the substrate. The 85% maintenance threshold ensures Masters don't degrade over time.

2.3 Promotion Mechanics — Step by Step

1 Attempt Recording — Every mutation outcome calls recordAttempt(executorId, success). This increments the attempt counter and recalculates the running success rate for the current tier only.

2 Eligibility Check — After each attempt, the system checks two conditions:

  • attempts >= tierDef.minimumAttempts — Has the executor done enough work?
  • successRate >= tierDef.promotionThreshold — Is the success rate high enough?

Both must be true. If either fails, promotionEligible stays false.

3 Promotion Execution — When eligible, promoteExecutor(executorId) is called. This:

  • Records the old tier in tierHistory with timestamp and attempt count at promotion
  • Advances currentTier to the next level
  • Resets all counters to zero — attempts, successes, failures, successRate
  • Sets promotionEligible back to false
Critical design choice: Counters reset on promotion. This means a Tier 2 executor starts fresh — their Tier 1 success rate doesn't carry forward. They must re-prove competence at the new, harder level. This prevents an executor from coasting on easy wins.

4 Tier Gate Enforcement — Before any mutation executes, isMutationAllowed() checks three dimensions against the executor's current tier:

  • Mutation type — Is this mutation type in the tier's allowedMutations list?
  • Scope width — Does the number of affected modules exceed maxScopeWidth?
  • Risk score — Does the mutation's risk score exceed maxRiskScore?

If any check fails, the mutation is rejected with a specific reason string (e.g., mutation_type_defense_rule_not_allowed_at_intermediate). The executor cannot bypass this.

3. Pre-Mutation: What Happens Before a Mutation Runs

3.1 Warm-Up Sequence

TRAINING Every mutation can be preceded by a 4-phase warm-up. This is mandatory for high-stakes mutations (complexity grade ≥ "complex").

PhaseWhat It TestsRequired?TimeoutWhat Happens If It Fails
schema_check Can the executor parse and validate input schemas? ✅ Yes 1000ms Mutation blocked. Executor cannot validate inputs — fundamentally unsafe.
repair_check Are deterministic repair strategies loaded and functional? ✅ Yes 1000ms Mutation blocked. Without repair, any malformed input causes hard failure.
shadow_dry_run Can the executor run a no-op shadow pass through the pipeline? ❌ Advisory 2000ms Warning logged. Pipeline connectivity may be degraded but not necessarily broken.
rollback_verify Is the rollback snapshot capability available? ✅ Yes 500ms Mutation blocked. Without rollback, any failure becomes permanent state corruption.
Readiness verdict: readyForMutation = true only if all required phases pass. The shadow dry run is optional — it can fail and the executor can still proceed, but the failure is logged and affects stamina metrics.

3.2 Mutation Complexity Scoring

DIAGNOSTICS Before execution, every proposed mutation is scored across 6 weighted dimensions:

DimensionWeightHow It's CalculatedWhat It Means
Scope Breadth 25% modulesAffected / 24 More modules = wider blast radius if something breaks.
Change Volume 15% linesChanged / 500 Larger changes are harder to review and rollback.
Safety Sensitivity 20% 0.4 if touches DEFENSE + 0.3 if routing + 0.3 if MEMORY Touching security/routing/memory surfaces compounds risk.
Test Coverage Gap 15% 1 - regressionTestCoverage Less coverage = more blind spots for regressions.
Historical Risk 10% previousFailures / 5 Past failures on similar mutations predict future failure.
Reversibility 15% 0 if reversible, 1.0 if not Irreversible mutations have no safety net.

The weighted sum produces an overall score (0.0–1.0) which maps to a grade and a recommended tier:

Score RangeGradeRecommended TierAction
< 0.15TrivialFoundationalExecute immediately
0.15–0.30SimpleIntermediateExecute with standard monitoring
0.30–0.50ModerateAdvancedRequire warm-up + shadow mode recommended
0.50–0.70ComplexExpertMandatory warm-up + shadow + rollback plan
> 0.70CriticalMasterAll safeguards + governance approval

Warnings are auto-generated for: no rollback plan, low test coverage (<50%), high historical failure rate (≥3), irreversibility, and DEFENSE module involvement.

4. During Mutation: What Gets Tracked in Real-Time

4.1 Micro-Feedback Loops

DIAGNOSTICS Every mutation runs inside a feedback session. Each logical step within the mutation is recorded as a MicroStep:

MicroStep {
  stepId:      "step_3"
  phase:       "schema_validation"
  description: "Validated input against executor schema"
  signal:      "positive" | "negative" | "neutral" | "inconclusive"
  durationMs:  42
  timestamp:   1740000000000
}

At session completion, the system auto-derives insights from the step sequence:

Insight TypeDetection LogicWhat It Means
Bottleneck Any step with durationMs > 500 That phase is slow — potential optimization target.
Cascade Failure 3+ consecutive negative signals Failure in one step is propagating downstream. Circuit breaker needed.
Input Quality Issue First step is negative The problem is at the entry point, not in the mutation logic.
Recovery Pattern Negative signal followed by all-positive remaining steps Executor self-corrected — repair pipeline is working.
Overall signal derivation:
• >30% negative steps → session is negative
• >60% positive steps → session is positive
• Mix of signals → neutral
• No positive or negative steps at all → inconclusive

4.2 Confidence Calibration

DIAGNOSTICS Before each mutation, the executor reports a predicted confidence (0.0–1.0). After the mutation, the actual outcome is recorded. These pairs are bucketed into 10 bins (0–10%, 10–20%, ... 90–100%) and analyzed:

MetricWhat It MeasuresHealthy Range
ECE (Expected Calibration Error) Weighted average of |predicted − actual| across all buckets < 0.05 = Excellent, < 0.10 = Good, < 0.20 = Fair, ≥ 0.20 = Poor
MCE (Maximum Calibration Error) Worst-case bucket miscalibration < 0.15
Bias Positive = overconfident (predicts high, fails often). Negative = underconfident. |bias| < 0.05

Why this matters: An overconfident executor will attempt mutations it can't handle and fail. An underconfident executor will avoid mutations it could succeed at, slowing evolution. Calibration is the meta-skill that governs all other skills.

Minimum data: Calibration reports require ≥10 data points. Below that, the executor is graded uncalibrated — no confidence data is reliable.

4.3 Stamina Tracking

DIAGNOSTICS Extended mutation sessions degrade executor quality. The stamina system tracks this in real-time via periodic checkpoints:

StaminaCheckpoint {
  mutationsCompleted:  45
  successRate:         0.82       ← compared to session baseline
  avgLatencyMs:        340        ← compared to session baseline
  repairRate:          0.15       ← compared to session baseline
}

Fatigue detection triggers when ≥2 of 3 signals appear:

  1. Success rate dropped ≥15% from session baseline
  2. Average latency increased ≥25% from session baseline
  3. Repair rate increased ≥20% from session baseline

When fatigue is detected:

  • fatigueDetected = true
  • fatigueOnsetMutation records the mutation count where quality started degrading
  • Recommended cooldown = 25% of session duration, capped at 6 hours

The getStaminaReport() aggregates across sessions to calculate optimalSessionLength — the recommended number of mutations before the executor should rest (80% of average fatigue onset point).

5. After Mutation: What Happens on Failure

5.1 Failure Taxonomy Classification

DIAGNOSTICS Every failure is classified into exactly one of 9 categories. Classification is automatic, based on error message pattern matching:

CategoryDetection PatternSeverityRoot CauseSuggested Action
input_quality "safe-fail", "archetype" Minor Malformed input structure Add pre-validation at entry point
schema_mismatch "schema", "validation" Minor Input doesn't conform to schema Update schema or add coercion rules
repair_exhaustion "no repair", "repair failed" Moderate All repair strategies exhausted Add new repair strategy or escalate
timeout "timeout", "timed out" Moderate Exceeded time budget Increase timeout or optimize pipeline
cascade_failure "cascade", "downstream" Critical Upstream failure propagated Isolate module + circuit breaker
resource_limit "limit", "quota", "memory" Minor–Moderate System resource constraint Review allocation + backpressure
governance_block "governance", "blocked", "denied" Severe Blocked by governance rules Request governance review
regression_detected "regression", "degradation" Critical Change caused regression Rollback + schedule RCA
unknown No pattern match Minor Unclassified Log for manual review
Severity auto-escalation: Cascade failures and regressions are always critical. Governance blocks are always severe. If any failure affects >3 modules, severity is elevated to severe regardless of category.

Repeat pattern detection: The system tracks same-category + same-archetype failures within 24-hour windows. If ≥3 repeats occur, a repeatPattern alert is generated — this signals a systemic issue, not a random failure.

Trend detection: Compares first-half vs second-half of failure history. If critical/severe failures decrease by >10%, trend is improving. If they increase by >10%, trend is degrading.

5.2 Post-Mortem Auto-Generation

DIAGNOSTICS Every classified failure with severity ≥ P2 automatically generates a structured post-mortem document:

PostMortem {
  severity:    P0 | P1 | P2 | P3
  timeline:    [ { timestamp, event, phase } ... ]
  rootCause:   { category, description, contributing[] }
  impact:      { modulesAffected, durationMs, rollbackRequired, dataLoss }
  resolution:  { action, preventionMeasures[] }
  lessons:     [ "Add pre-flight schema validation...", ... ]
  tags:        [ "schema_violation", "validation", "type_mismatch" ]
}

Severity assignment:

  • P0 — Rollback required AND >5 modules affected
  • P1 — Rollback required OR >3 modules affected
  • P2 — >1 module affected
  • P3 — Single module, contained failure

Auto-derived lessons are category-specific:

  • schema_violation → "Add pre-flight schema validation before mutation entry"
  • repair_gap → "New repair strategy needed — add to deterministic repair engine"
  • performance → "Profile mutation pipeline for bottlenecks"
  • architecture → "Implement circuit breakers between critical module boundaries"

Auto-derived prevention measures:

  • schema_violation → Add schema pre-check to warm-up + extend validation coverage
  • repair_gap → Implement new repair strategy + add gap to replay sandbox
  • performance → Add timeout budget to complexity score + implement progressive execution
  • architecture → Add circuit breaker + limit mutation scope width

Post-mortems are searchable by tag, root cause category, and severity.

5.3 Gap Capture & Replay Sandbox

TRAINING When a mutation fails, the exact input, error, archetype, and attempted repair strategies are captured as a GapSnapshot:

GapSnapshot {
  id:                        "gap_12_1740000000000"
  executorId:                "exec_alpha"
  originalInput:             { ... deep clone ... }
  originalError:             "schema validation failed: missing field 'email'"
  archetype:                 "missing_required"
  repairStrategiesAttempted: ["null_coerce", "default_fill"]
  replayCount:               0
  resolved:                  false
}

Replay mechanics:

  1. The executor calls replayGap(snapshotId, handler) with a new handler function
  2. The system deep-clones the original input and feeds it to the handler
  3. If the handler succeeds → gap marked resolved, resolution strategy and attempt count recorded
  4. If the handler fails → replayCount incremented, system checks if the error is different from the original (partial improvement = improvementOverOriginal: true)

Stats tracked: total gaps, resolved count, unresolved count, average attempts-to-resolve, resolution rate. These feed into the repair effectiveness tracker.

6. Ongoing: Skill Monitoring & Decay Detection

6.1 Skill Decay Analysis

DIAGNOSTICS Skills degrade over time without practice. The system monitors this via 7-day sliding windows:

1 Every mutation records a SkillEvent → { executorId, skillKey, success, timestamp }

2 analyzeSkillDecay() builds time windows from the first event to now, each 7 days wide

3 Compares current window's success rate against historical peak

4 Generates alerts based on three patterns:

Alert TypeTriggerSeverityRecommendation
performance_decay ≥15% drop from peak success rate (gradual) Medium (≥30% → High) "Gradual decay in [skill] — assign targeted practice"
inactivity_decay No activity for ≥14 days Medium (≥30 days → High) "Executor inactive for N days — schedule refresh drills"
sudden_drop ≥25% drop between two consecutive windows High "Sudden N% drop — investigate recent mutations + rollback drill"

7. Repair Strategy Effectiveness

DIAGNOSTICS Every repair attempt records: { strategy, archetype, executorId, success, durationMs }. The system tracks:

  • Per-strategy effectiveness: Overall success rate, average duration, per-archetype breakdown
  • Ranked strategy list: All strategies sorted by success rate — used to prioritize which strategy to try first
  • Best strategy per archetype: Given an archetype (e.g., type_mismatch), returns the strategy with highest success rate
  • Trend detection: Compares first-half vs second-half of strategy records. If success rate improves by >5%, trend is improving. If it drops by >5%, trend is declining.

This closes the loop: failure taxonomy identifies what went wrong → repair effectiveness tracks which fix works → pattern library codifies the winning approach.

8. Rollback Drills

TRAINING Structured practice for high-pressure revert operations. 6 scenarios, escalating in difficulty:

ScenarioDifficultyModulesCorruption?Time PressureWhat It Tests
Single Prompt Revert Easy 1 No None Basic revert mechanics — can you undo a single change cleanly?
Routing Weight Rollback Easy 2 No 30s Multi-module revert under mild time pressure. Tests coordination.
MEMORY Decay Correction Medium 3 No 20s Reverting a change whose effects are delayed (context loss is gradual).
DEFENSE Rule Revert Medium 4 Yes 15s Rollback with partial state corruption. Must identify what's corrupted before reverting.
Pipeline Cascade Failure Hard 8 Yes 10s Full pipeline rollback under extreme time pressure with corruption. Tests composure.
Multi-EVOLUTION Stack Unwind Hard 12 Yes 8s Unwind 3 stacked evolutions to a stable baseline. The hardest drill — requires understanding mutation dependencies.

Stats tracked per executor: total drills, success rate, average duration, fastest drill, time-pressure success rate, and success rate broken down by difficulty level.

Time pressure is real: withinTimePressure is only true if the drill completes in fewer milliseconds than timePressureMs. An executor can succeed but fail the time pressure check — this is tracked separately because in production, slow rollbacks extend outage duration.

9. Knowledge Architecture

9.1 Pattern & Anti-Pattern Library

KNOWLEDGE 8 seed entries (5 patterns, 3 anti-patterns), RCA-indexed. Each entry includes:

  • applicableWhen — Precise conditions where this pattern should be used
  • guidance — Specific instructions (do this / never do this)
  • rcaCategories — Which root cause analysis categories this maps to (for failure-driven lookup)
  • archetypes — Which input archetypes this applies to
  • observedSuccessRate — Empirical success rate when this pattern is followed
  • referenceCount — How many times this pattern has been applied (popularity signal)

Lookup paths:

  • findPatternsByRCA("schema_violation") → Returns all patterns/anti-patterns relevant to schema failures
  • findPatternsByArchetype("type_mismatch") → Returns patterns for that input type

New patterns are added via addPattern() as the executor discovers what works. The library grows organically.

9.2 Domain Specialty Trees

KNOWLEDGE A 23-node skill tree across 5 domains with parent→child unlock mechanics:

DomainRootChildren (unlock threshold)Grandchildren
Repair Repair Fundamentals Null Coercion (60%), Type Casting (60%), Input Sanitization (60%) Multi-Strategy Chains (70%) → Novel Pattern Repair (75%)
Schema Schema Mastery Archetype Classification (60%), Deep Validation (60%) Schema Evolution (70%)
Routing Routing Fundamentals Weight Adjustment (60%), Failover Logic (60%) Adaptive Routing (70%)
DEFENSE Defense Basics Threat Detection (60%) Rule Creation (70%) → Adaptive Defense (80%)
EVOLUTION Evolution Core Proposal Generation (60%), Rollback Operations (60%) Shadow Testing (70%) → Pipeline Restructure (80%)

Unlock mechanics:

  1. Root nodes are always unlocked — executors start with access to fundamentals
  2. Children unlock when their parent's mastery score exceeds the child's unlockThreshold
  3. Mastery = successes / attempts at that specific node
  4. When a child unlocks, recordSpecialtyAttempt() returns it in the newUnlocks array

Snapshot provides: per-domain mastery, strongest domain, weakest domain, overall mastery score.

9.3 Knowledge Packs

KNOWLEDGE Exportable bundles of curated knowledge with a lifecycle:

Status lifecycle: draft → reviewed → published → deprecated

Contents of a pack:

  • Curated patterns with observed success rates
  • Repair strategies with confidence scores
  • Configuration recommendations with rationale

Import safety gates:

  • Only published packs can be imported
  • Self-import is blocked (executor cannot import their own pack)
  • Strategies with confidence < 0.6 are auto-skipped
  • Patterns with success rate < 0.5 are auto-skipped
  • Skipped items are reported in the ImportResult

10. Deliberately Excluded

The following capabilities were evaluated and intentionally excluded from this build:

Cross-Executor Knowledge Transfer — Introduces contamination risk, blurs performance attribution, complicates debugging, makes failures harder to trace. Early evolution needs isolation. Each executor must prove competence independently.

Progressive Autonomy Unlocks — Permission systems before stability create chaos. Build when executor volume reaches 10x current levels. The difficulty ladder provides sufficient gating for now.

Risk Intuition Training — Useful calibration tool but not core to the repair/build loop. The confidence calibration tracker provides the necessary self-awareness signal.

Synthetic Gap Generator — Synthetic environments often create false confidence. Real gaps via the Replay Sandbox provide authentic training material. Synthetic generation deferred to Phase 2.
