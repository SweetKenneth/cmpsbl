1. Overview

CORE is the standalone kernel of the CMPSBL Substrate. It is the first entity to boot and the only entity with zero dependencies. Everything else — CCR, CCL, modules, meshes, and INTEGRATION — depends on CORE.

2. Responsibilities

2.1 Boot Sequence Management

CORE manages the entire substrate boot lifecycle through a state machine:

BOOT → KERNEL → COGNITIVE → OPERATIONAL → ADMINISTRATIVE → COMPLETE

Functions: initializeBootSequence(), markModuleBooted(), markModuleFailed(), completeBootSequence()

2.2 Module Registry

CORE maintains the canonical registry of all 25 substrate entries (15 public + 9 facades + 1 absorbed). It provides:

  • SUBSTRATE_MODULES — Full list of all module identifiers
  • PUBLIC_MODULE_COUNT — 15 (the public count)
  • CCR_FACADE_MODULES — system, brain, memory, dream
  • CCL_FACADE_MODULES — ripple, access, identity, relay, audit
  • ABSORBED_FACADES — modernizer (→ EVOLUTION)
  • MODULE_LAYERS — Layer classification for each entry

2.3 Circuit Breaker Coordination

Per-module circuit breakers prevent cascade failures. CORE provides the health-checking infrastructure, while individual modules and layers maintain their own breaker state.

2.4 Job Scheduling

Priority-based job scheduler with:

  • Priority queues: critical, high, normal, low
  • Retry logic with exponential backoff
  • Timeout protection
  • Job status tracking

2.5 Configuration Management

CoreConfig {
  debug_mode: boolean;          // Enable verbose logging
  strict_governance: boolean;   // Enforce GOVERNANCE mesh
  event_logging: boolean;       // Log all events
  performance_tracking: boolean;// Track timing metrics

2.6 Error Boundary Wrappers

safeExecute(module, operation, fn, fallback?) — Wraps any async operation with error handling, logging, and optional fallback values. Used throughout the substrate to prevent unhandled exceptions from crashing the system.

4. Health Monitoring

CORE provides system-wide health aggregation:

  • getSubstrateHealth() — Average health across all initialized modules (0–100)
  • getModuleStatuses() — All module statuses
  • updateModuleHealth(module, health) — Update individual module health
  • isSubstrateReady() — True when boot is complete and successful

6. Why CORE Is Standalone

CORE was briefly absorbed into CCR (Layer 0) but was re-separated because:

  1. Circular dependency — CCR depends on CORE for boot infrastructure. Absorbing CORE into CCR creates a logical paradox.
  2. Visibility — The kernel must be explicitly named and visible. Hiding it behind "Layer 0" obscures the most critical component.
  3. Failure isolation — If CORE fails, the diagnosis must be immediate. CCR masking would add indirection to failure analysis.
  4. Conceptual clarity — CORE is infrastructure; CCR is cognition. They serve fundamentally different purposes.
