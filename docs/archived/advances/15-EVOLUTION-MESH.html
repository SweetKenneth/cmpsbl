Abstract

Evolution Mesh is a framework-agnostic SDK that gives any JavaScript or TypeScript async function an adaptive immune system. It is a hybrid architecture combining two prior novel contributions from the CMPSBL OS Substrate: the Immunity Mesh (self-healing runtime defense) and the Bounded Self-Evolution Architecture (SEBA) (governed recursive improvement). The result is a system that validates inputs, classifies threats, repairs malformed data deterministically, learns from successful repairs, and continuously improves — all without requiring AI inference at runtime.

The SDK ships with a complete executor training pipeline, enabling rapid onboarding: any new function wrapped with Evolution Mesh inherits the collective defenses, repair strategies, and learned rules accumulated across the entire fleet of protected executors.

1. Motivation & Prior Art Gap

Traditional software defense falls into discrete categories — input validation (Zod, Joi), chaos engineering (Chaos Monkey), service mesh routing (Istio), and runtime protection (WAFs). None of these systems combine all four capabilities, and critically, none of them learn from their own repairs to improve over time.

2. Architectural Heritage

Evolution Mesh is not a standalone invention — it is the productized intersection of two substrate systems:

2.1 — Immunity Mesh (Defense Layer)

The Immunity Mesh (Chapter 05) provides the runtime defense foundation:

  • Input archetype classification — Every input is classified into one of eight archetypes (well-formed, empty shell, type mismatch, missing required, oversized, injection attempt, shape alien, partial valid)
  • Deterministic repair engine — A battery of non-AI repair strategies that attempt to fix malformed inputs before they reach business logic
  • Safe-fail protocol — Irreparable inputs are rejected gracefully with structured error reporting, never crashing the host
  • Shared rule registry — Successful repairs generate learned rules that propagate to other protected functions

2.2 — SEBA (Evolution Layer)

The Bounded Self-Evolution Architecture (Chapter 03) provides the governed improvement foundation:

  • Shadow execution — Candidate code paths run in parallel with production, with results compared but never affecting real traffic
  • Risk-gated promotion — Changes only apply if they pass regression gates, performance benchmarks, and governance bounds
  • Rollback atomicity — Every promotion captures a full state snapshot enabling instant, atomic rollback
  • Budget constraints — Rate limits prevent runaway evolution

Evolution Mesh extracts these capabilities into a portable SDK, decoupled from the CMPSBL substrate infrastructure.

3. The Core Primitive: wrap()

The entire SDK surface reduces to a single function:

import { wrap, defineSchema } from '@cmpsbl/evolution-mesh';

const protectedEndpoint = wrap(myHandler, {
  schema: defineSchema({
    email: { type: 'string', required: true },
    age: { type: 'number' },
  }),
  category: 'user-management',
});

// Every call now has immune defense
const result = await protectedEndpoint({ email: 'test@test.com', age: 25 });

When wrap() is called, the following lifecycle executes transparently:

Input → Schema Validation → Archetype Classification
  ↓
  ├─ well_formed → Execute → Track Outcome
  ├─ repairable (type_mismatch, missing_required) → Repair → Execute → Track
  ├─ unrepairable (injection, shape_alien) → Safe-Fail → Track
  └─ execution failure → Re-validate → Retry with Repair → Escalate

4. Input Archetype Classification

Every input is classified into one of eight archetypes before any business logic executes:

ArchetypeDescriptionRepair Policy
well_formedPasses all schema checksExecute directly
empty_shellEmpty object or all null valuesSafe-fail immediately
type_mismatchCorrect keys, wrong value typesAttempt repair
missing_requiredCritical fields absentAttempt repair
oversizedValues exceed size boundsSafe-fail immediately
injection_attemptSQL/XSS/prototype pollution detectedSafe-fail immediately
shape_alienNo recognized keys match schemaSafe-fail immediately
partial_validMixed: some fields valid, some notContext-dependent

The classification determines whether the system attempts repair or immediately safe-fails. This gating prevents wasted computation on clearly adversarial or garbage inputs.

5. Deterministic Repair Engine

The repair engine contains 29+ non-AI repair strategies that execute in a fixed priority order. No external model calls are required — all repairs are pure, deterministic transformations:

  • Type coercion — Booleans and numbers converted to strings for string-typed fields
  • Null normalization — Null/undefined values replaced with safe defaults
  • Size clamping — Oversized strings and arrays truncated to safe bounds
  • Injection sanitization — SQL keywords, XSS payloads, and script tags neutralized
  • Prototype pollution guard — Dangerous keys (__proto__, constructor) stripped
  • Path traversal stripping — Directory traversal sequences removed
  • Control character removal — Non-printable characters stripped
  • Zero-width character removal — Invisible Unicode characters stripped
  • HTML entity encoding — Angle brackets encoded to prevent injection
  • Whitespace normalization — Excessive whitespace collapsed
  • Array flattening — Arrays in string-typed fields joined to comma-separated values
  • JSON recovery — Malformed JSON strings parsed and reconstructed
  • Enum clamping — Invalid enum values mapped to nearest valid option
  • URL normalization — Malformed URLs cleaned and validated
  • Emoji flood collapse — Excessive emoji sequences condensed

Each strategy is idempotent and composable — multiple strategies may fire on the same input, and the result is always safe for downstream consumption.

6. Cross-Function Learning

When a repair strategy succeeds (the repaired input produces a valid execution), the system records a learned rule. These rules propagate to other wrapped functions in the same category, enabling collective immunity:

Learning Loop:

Function A receives type_mismatch → Repair succeeds
  → Rule generated: "type_mismatch + COERCE_TYPE → success"
  → Rule propagated to Functions B, C, D (same category)
  → Future type_mismatch inputs in B, C, D benefit immediately

Rules carry confidence scores that adjust over time:

  • Successful applications increase confidence
  • Failed applications decrease confidence
  • Rules that fall below a minimum confidence threshold after sufficient invocations are automatically demoted and removed
  • Category boundaries prevent inappropriate rule leakage (security rules don't propagate to content handlers)

7. Shadow Execution Mode

Evolution Mesh includes a shadow execution engine inherited from SEBA. This enables safe testing of changes against real traffic:

import { shadow } from '@cmpsbl/evolution-mesh';

const result = await shadow(
  currentHandler,    // baseline — serves real traffic
  candidateHandler,  // candidate — runs in parallel, result discarded
  inputData,
);

// result.baseline — actual response (returned to caller)
// result.candidate — candidate response (logged for comparison)
// result.match — whether outputs were equivalent
// result.durationMs — timing for both paths

Shadow mode enables zero-risk A/B testing of repair strategies, routing changes, and handler updates before promotion to production.

8. Executor Training Pipeline

A critical differentiator of Evolution Mesh is its inclusion of a complete training pipeline for executor onboarding. When a new function is wrapped, it does not start from zero — it inherits:

8.1 — Inherited Defenses

  • All 29+ deterministic repair strategies active from first invocation
  • Schema validation engine with full archetype classification
  • Injection detection (SQL, XSS, prototype pollution, path traversal)
  • Safe-fail protocol with structured error reporting

8.2 — Inherited Knowledge

  • Existing learned rules from the shared rule registry (filtered by category compatibility)
  • Proficiency baselines from the executor training system (Probe Mode and Build Mode)
  • Historical repair success rates that inform strategy priority

8.3 — Training Modes

The SDK supports two training modes that exercise wrapped functions under controlled conditions:

  • Probe Mode: Adversarial stress testing — deliberately malformed inputs are generated to test defense coverage and discover repair gaps
  • Build Mode (Shadow Build): Real-world task simulation using replay data, synthetic inputs, and ENCODE-generated scenarios. A Proficiency EMA (Exponential Moving Average) tracks skill development per executor-skill pair

Successful training outcomes automatically feed into the shared rule registry, accelerating collective defense maturation.

9. Telemetry & Observability

Every execution through wrap() is tracked with structured telemetry:

  • Outcome classification: success, repaired_success, safe_fail, escalated
  • Per-function metrics: success rate, repair rate, escalation count, average latency
  • Archetype distribution: which input archetypes appear most frequently per function
  • Repair effectiveness: which strategies fire most often and their success rates

Telemetry can be consumed locally (in-memory) or streamed to the SaaS dashboard for fleet-wide visibility. The dashboard provides health overviews, repair analytics, learning curve visualization, and an alert feed for escalations and new attack patterns.

11. SDK Distribution

Evolution Mesh ships as an npm package (@cmpsbl/evolution-mesh) with the following public API surface:

// Core wrapper
wrap(fn, config?)         — Wrap any async function with immune defense
defineSchema(fields)      — Declare input schema for validation

// Shadow mode
shadow(baseline, candidate, input) — Safe A/B testing

// Observability (read-only)
getMetrics()              — Execution statistics
getRules()                — Active learned rules
getRepairStats()          — Repair engine statistics
getPerformanceStats()     — Per-function performance data

// Configuration
configure(options)        — Global SDK settings

The SDK is compiled and minified for distribution. Source maps are excluded. Internal repair strategies and learning algorithms are proprietary.

12. Relationship to the CMPSBL OS Substrate

Within the CMPSBL OS Substrate, Evolution Mesh operates as the unified defense and evolution layer:

  • IMMUNITY MESH — provides the runtime defense primitives (validation, classification, repair, safe-fail)
  • SEBA — provides the governed evolution primitives (shadow mode, risk gates, rollback, budgets)
  • CLM (Constant Learning Machine) — feeds domain knowledge that enriches learning rules
  • MEMORY — stores and retrieves learned patterns with spaced-repetition degradation
  • CORTEX — enforces governance boundaries on evolution proposals
  • ENCODE — generates synthetic training scenarios for Build Mode

The SDK extracts the defense and evolution capabilities into a standalone package that operates without the full substrate, while the substrate itself uses Evolution Mesh internally for its own executor protection.
