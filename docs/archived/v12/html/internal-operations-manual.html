3. Constant Learning Mode (CLM)

CLM is the substrate's always-on, rate-limited, spaced learning engine. It operates at two levels:

3.1 Architecture

ComponentFilePurpose
Budget Governorclm/budget-governor.tsDynamic budget allocation via NEXUS 4-hour cycles. Manages daily limits, backoff, quiet hours, micro-learning mode.
Topic Bankclm/topic-bank.tsCurated curriculum with weighted selection: 50% core curriculum, 25% gap detection, 15% spaced repetition, 10% deep dives.
Spaced Repetitionclm/spaced-repetition.tsSM-2 scheduling for memory consolidation. Capped at 30% of daily CLM budget.
Orchestratorclm/orchestrator.tsCoordinates the learning loop: select topic → check budget → build job → execute → reflect → update graph → dream/prune.
Encoded Learning Engineclm/encoded-learning-engine.ts24/7 code-writing mastery engine. Runs every 15 minutes. Dedicated curriculum for TypeScript/React patterns.
Tier Commandclm/tier-command.tsTier-based governance: free, standard, pro, enterprise. Controls budget limits, spacing, concurrency.
Deep Dive URLsclm/deep-dive-urls.tsCurated external knowledge sources (OWASP, React docs, pgvector, etc.) for real-world knowledge ingestion.
React Hookclm/useCLM.tsReact integration: useCLM() provides state, actions, and refresh for UI components.

3.2 How CLM Works — Full Lifecycle

  1. Budget Sync: On initialization, the Budget Governor reads nexus_clm_budget from system_flags. If fresh (< 2 hours old), it uses the NEXUS optimizer's calls_per_hour. Otherwise, falls back to the adaptive-budget 4-hour cycle allocator.
  2. Execution Check: canExecute() validates: kill switch off, CLM enabled, not paused from errors, not in quiet hours (default 03:00–05:00), budget remaining, spacing respected.
  3. Topic Selection: The Topic Bank selects from core curriculum (20+ topics across all modules), gap detection, spaced repetition queue, and deep dives. Weighted by priority, mastery, and recency.
  4. Job Execution: The Orchestrator calls pf-nexus-router edge function with the constructed prompt. NEXUS routes to the cheapest available AI provider.
  5. Knowledge Storage: Results go through learningEngine.input() which routes to memoryCore.ingest() with a confidence cap of 0.55 to prevent CLM data from flooding the hot tier.
  6. Reflection: After each job, memoryCore.reflect() generates cross-domain insights, stored at confidence 0.5 (warm tier).
  7. Graph Update: Knowledge nodes and edges are written to brain_graph_edges with learning relations, concept-module links, and topic-concept connections.
  8. Dream/Prune: Every 6 jobs, runs auto-degradation (warm → cold for 14+ day stale memories), then pf-brain-memory-prune and pf-dream-cycle.

3.3 Dual Execution Model

Server-side primary + Client-side supplementary

The primary CLM engine runs server-side via pf-clm-engine (pg_cron, every 5 minutes), achieving up to 14,400 AI calls per day with 65-cycle/hour cap and self-chaining logic. The client-side orchestrator is supplementary — it runs only when a browser tab is open, providing additional learning capacity.

3.4 Starting CLM

Option A: Automatic (Production)

CLM starts automatically when the substrate initializes. The server-side engine (pf-clm-engine) runs via pg_cron and requires no user intervention. As long as:

  • At least one AI provider key is configured in backend secrets
  • The system_flags table has auto_training_enabled = true
  • Kill switch is not active

3.5 Encoded Learning Engine (Code-Writing Mastery)

The Encoded Learning Engine is a dedicated 24/7 engine focused exclusively on code-writing improvement. It has its own curriculum (50+ topics covering TypeScript patterns, React anti-patterns, testing strategies, performance optimization, etc.).

  • Cycle interval: Every 15 minutes
  • Topic selection: Weighted by priority (40%), inverse mastery (40%), topic weight (20%)
  • Focus rotation: Randomly cycles between pattern, anti-pattern, best-practice, technique, and review modes
  • Mastery tracking: Per-topic mastery scores (0.0–1.0) persisted in localStorage
  • Storage: Patterns stored as high-confidence (0.9) heuristics; anti-patterns stored as warnings

4. System Scanning & Proposal Engine

4.1 Unified Proposal Generator (v3.3.1)

The proposal engine aggregates findings from 10 audit sources:

  1. SEBA Evolution
  2. Full Audit Runner
  3. Substrate Health Check
  4. AUDIT Compliance Ledger
  5. Diligence Harness
  6. ENGINEER Maintenance Node
  7. INTEL Aggregator
  8. INCLUSIVE (accessibility)
  9. DEFENSE (security)
  10. MODERNIZER (4-phase cognitive scan)

4.2 Rules

  • Maximum 5 action steps per proposal run
  • 60/40 ratio: 60% technical debt elimination, 40% system evolution
  • Priority order: structural integrity → production audit fatals → technical debt → diligence → accessibility → security → evolution
  • Guaranteed evolution: If all layers pass with zero fatals and zero critical debt, evolution always fires (v3.3.1 fix)
  • False-positive filtering: DEFENSE ignores single-IP traffic (dev environments) and "0 fingerprint families" data bugs
  • Human-in-the-loop: All proposals require explicit approval before external AI execution

4.3 Output Format

Each proposal produces a JSON report containing:

  • executive_summary — High-level assessment with health grade
  • stability_assessment — Per-layer pass/fail with zero-fatal confirmation
  • action_plan — Up to 5 prioritized steps with category tags
  • evolution_opportunities — CLM topic selection, system hardening recommendations
  • metadata — Timestamp, version, source count, confidence score

5. Evolution & Mutation Engine

5.1 External-AI Execution Mode

The substrate never self-mutates. All evolution operates in "external-ai" mode. Mutation authority is removed from the runtime and delegated to an external AI execution loop. Internal code execution or auto-application of proposals is strictly forbidden.

5.2 Lifecycle

  1. Pre-generation rollback snapshot (mandatory)
  2. Modernizer governance chain: verify → diffs → receipts (deterministic hashes)
  3. SEBA choreographical stamping: lineage_id + signature
  4. Export: POST /evolution/export returns stamped JSON proposal
  5. External application: External AI applies the proposal
  6. Recording: POST /evolution/applied records the application

5.3 Promotion Pipeline (7 Gates)

Shadow → Simulation → Preflight → Canary → Production, with 12 stabilization gates including TSAC shadow verdicts and Integrity Health Score (≥ 60%).

6.2 CLM Confidence Caps

CLM learning outputs are capped at confidence 0.55 to prevent flooding the hot tier. Reflections are capped at 0.5. Only user-generated facts, preferences, and task outcomes can reach full confidence.

6.3 Adaptive Limits

The get_adaptive_memory_limits() function scales tier capacity based on user activity: total recalls, recall hit rate, and an activity multiplier (logarithmic scaling). High recall rate (> 70%) gets a 1.5× bonus.

7. Budget Governance & NEXUS Allocation

7.1 Dynamic Budget (No Hardcoded Percentages)

CLM budget is computed dynamically by NEXUS every 4 hours:

  1. NEXUS calculates total available API calls for the cycle
  2. Subtracts estimated operational needs (routing, scanning, etc.)
  3. Divides surplus equally among learning entities
  4. Entities rapid-fire until allocation exhausted or next cycle

7.3 Discovery Phase

When nexus_clm_budget.phase === 'discovery', the system switches to aggressive learning: 1-minute spacing, 6 concurrent jobs, no quiet hours, 0.5-minute jitter. This is used during initial onboarding to build foundational knowledge rapidly.

8.2 How to Configure

  1. Open Clockless Cloud backend secrets manager
  2. Add the provider key(s) as secrets
  3. The NEXUS router will automatically detect and use available providers
  4. No code changes required — provider availability is detected at runtime

8.3 No Keys = No Learning

CLM will not function without at least one AI provider key. The system will continue to run but all learning cycles will fail, trigger exponential backoff, and eventually auto-pause after 5 consecutive failures. The substrate's operational features (auth, database, etc.) are unaffected.

8.4 Secrets Vault (pf-vault)

For internal module use, the substrate includes a Secrets Vault providing AES-GCM encrypted storage with per-module access scoping, rotation support, and audit logging via vault_access_log.

9. Module CLM Integration

Each substrate module exposes a CLM cycle function that generates a CLMReport containing:

  • module — Module identifier
  • cycleId — Unique cycle identifier
  • learnings — Array of diagnostic strings
  • proposedUpgrades — Implemented features + pending recommendations
  • risks — Active risks detected
  • confidence — Module confidence score (0.0–1.0)

These reports feed into the memory core (memoryCore.remember()) and emit events via the substrate event bus for aggregation by the INTEL module.

11. Safety & Kill Switches

11.1 Kill Switch

activateKillSwitch() immediately halts all CLM activity and stops the Encoded learning engine. Can be triggered via terminal (clm.kill) or programmatically.

11.2 Auto-Pause

After 5 consecutive failures (configurable via maxConsecutiveFailures), CLM auto-pauses and emits a clm_auto_disabled brain event. Resume with clm.resume.

11.3 Circuit Breakers

Each module has independent circuit breakers (closed/half-open/open) that protect against cascading failures. Module CLM cycles report circuit state in their CLMReport.

11.4 Governance Modes

The governance_mode table controls system-wide operational mode with auto-revert TTL:

  • ACTIVE: Normal operation — all subsystems running
  • MAINTENANCE: Reduced operations — CLM paused, evolution blocked
  • EMERGENCY: Critical only — all learning and evolution halted

11.5 Builder Isolation

User projects run on the substrate, never as the substrate. Internal systems (CLM, MODERNIZER, SEBA, ENCODE, CORTEX, GOVERNOR, SYSTEM) are first-party and non-exportable.
