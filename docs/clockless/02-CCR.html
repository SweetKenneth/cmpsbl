1. Overview

CCR (Clockless Cognitive Reality) is the Layer 0 meta-engine of the CMPSBL Substrate. It is a hidden, non-marketed convergence layer that consolidates the cognitive and administrative foundations of the system.

PropertyValue
Layer0 (boots after CORE)
VisibilityHidden — not shown in public registries
AbsorbsSYSTEM, BRAIN, MEMORY, DREAM
Feature FlagsetCCREnabled(bool)

2. Absorbed Modules

2.1 SYSTEM

Administrative control surface. Configuration management, system diagnostics, maintenance mode toggling. CCR maps system.status, system.config, system.boot to internal handlers.

2.2 BRAIN

The reasoning engine. Higher-order reasoning, causal analysis, hypothesis testing. CCR maps brain.reason, brain.status, brain.pulse to internal handlers. The reasoning engine supports structured queries with context injection and confidence scoring.

2.3 MEMORY

Multi-tier persistent memory. Supports hot/warm/cold/frozen tiering with automatic promotion and demotion. CCR maps memory.store, memory.retrieve, memory.search to internal handlers. Protected memories (identity, principles, safety) are immutable.

2.4 DREAM

Synthesis and imagination engine. Pattern fusion, creative synthesis, latent content processing. CCR maps dream.synthesize, dream.status, dream.pulse to internal handlers. Dream synthesis operates asynchronously and records the last synthesis timestamp.

4. Circuit Breaker

CCR has its own circuit breaker isolated from CORE's per-module breakers:

ParameterValue
Failure threshold5 consecutive failures
Recovery timeout30,000ms
Success threshold3 consecutive successes
Monitoring window60,000ms

When the circuit opens, all CCR operations return immediately with a circuit-open signal. After the recovery timeout, the circuit enters half_open state and allows test operations. Three consecutive successes close the circuit.

6. Facade Routing

The module-to-CCR action mapping ensures backward compatibility:

MODULE_ACTION_MAP = {
  system: { status → status, health → health, boot → boot, config → config, pulse → pulse },
  brain:  { status → status, reason → reason, pulse → pulse, health → health },
  memory: { status → status, store → store, retrieve → retrieve, search → retrieve, pulse → pulse },
  dream:  { status → status, synthesize → synthesize, pulse → pulse, health → health },
}

When a request like { module: 'brain', action: 'reason' } arrives at the substrate router, resolveCCRAction('brain', 'reason') returns 'reason', and CCR's internal reason() handler is invoked.

7. Health Calculation

CCR health is the average of two scores:

  • state.health — Overall CCR operational health
  • state.memoryStoreHealth — Memory subsystem health

Both start at 100 and degrade on failures. The circuit breaker state is reported alongside but does not directly affect the health score.

9. Why CORE Is Not Part of CCR

CORE was originally absorbed into CCR but was re-separated for three reasons:

  1. Boot Dependency — CCR itself depends on CORE. A circular dependency is architecturally invalid.
  2. Visibility — The kernel should be explicitly visible in the architecture, not hidden behind a meta-engine.
  3. Failure Isolation — CORE failures must be immediately diagnosable. Masking them behind CCR would delay detection.

CORE boots first, then CCR boots on top of it. This is the correct dependency order.
