1. What Is Clockless?

Clockless describes the behavioral property of the CMPSBL Substrate: it operates without fixed scheduling cycles, wall-clock dependencies, or synchronous heartbeats. Instead, the system is event-driven, intent-reactive, and self-pacing.

A Cognitive Reality is a persistent environment defined by three properties:

  1. Memory — The system remembers across sessions, actors, and contexts
  2. Identity — Every actor, module, and event has provenance
  3. Autonomous Evolution — The system improves itself through governed mutation

Together, "Clockless Cognitive Reality" means: a self-aware, self-improving intelligence substrate that operates asynchronously and persists indefinitely.

2. Architecture Overview

The substrate is organized into 15 public entities and 2 hidden convergence layers.

3. Boot Sequence

The substrate boots in strict dependency order:

Phase 1: CORE ← Standalone kernel boots first Phase 2: CCR ← Layer 0 — cognitive foundation Phase 3: CCL ← Layer 1 — infrastructure convergence Phase 4: Modules ← 8 public modules (parallel) Phase 5: Meshes ← 5 cross-cutting meshes (parallel) Phase 6: INTEGRATION ← External service connections

Each phase validates circuit breaker state before proceeding. If CORE fails, nothing boots. If CCR fails, modules fall back to individual pings. If CCL fails, infrastructure operates in degraded mode.

4. CCR — Clockless Cognitive Reality (Layer 0)

4.1 Purpose

CCR is the hidden cognitive foundation of the substrate. It was created by merging SYSTEM, BRAIN, MEMORY, and DREAM into a single meta-engine. CORE was separated back out to serve as the standalone kernel.

4.2 Absorbed Modules

4.3 Facade Behavior

Legacy commands like brain.reason, memory.store, dream.synthesize, and system.config continue to work. They are intercepted by the substrate router and dispatched to CCR internals via the resolveCCRAction() mapping.

4.4 Circuit Breaker

CCR has its own circuit breaker with configurable thresholds:

  • Failure threshold: 5 consecutive failures
  • Recovery timeout: 30 seconds
  • Success threshold: 3 consecutive successes to close

4.5 Feature Flag

setCCREnabled(false) disables all CCR routing, causing facade modules to fall back to their original implementations (if available). This supports rollback.

5. CCL — Clockless Cognitive Lucidity (Layer 1)

5.1 Purpose

CCL is the infrastructure convergence layer. It consolidates all cross-cutting infrastructure services into a single initialization and health surface.

5.3 Health Check Binding

The Substrate Health Check binds to CCL via the integrity subsystem. This is a read-only surface — it verifies registry shape, route integrity, pipeline crystallization, edge functions, and RLS behavior but never mutates state.

5.4 Facade Behavior

Legacy commands like access.status, relay.deliver, ripple.emit, identity.session, and audit.status route through CCL's resolveCCLAction() mapping.

6. CORE — Standalone Kernel

6.1 Why CORE Is Separate

CORE was originally absorbed into CCR but has been re-separated as a first-class standalone kernel. Reasons:

  • Boot dependency — Everything depends on CORE, including CCR and CCL
  • Clarity — The kernel should be explicitly visible, not hidden
  • Isolation — CORE failures should be immediately obvious, not masked by CCR

6.2 Responsibilities

  • Boot sequence management
  • Circuit breaker coordination
  • Job scheduling (priority queues, retry logic)
  • Module registry and dependency graph
  • Configuration management
  • Error boundary wrappers

10. Substrate Health Check

The Substrate Health Check is a read-only integrity primitive that validates:

  1. Filesystem — Module directories, audit check files
  2. Imports — Critical import chains resolve
  3. Terminal — Command handlers are registered
  4. Routes — Critical routes resolve without 404
  5. Registry — Crystallized pipelines have valid shape
  6. Edge Functions — Active functions are declared
  7. Database Security — RLS enforcement is active
  8. Runtime Render — React root present, no fatal errors

The health check is bound to CCL's integrity subsystem. It never mutates state and never auto-fixes. A 400/401 from RLS is treated as PASS (confirming security boundaries are active).

11. Rollback Strategy

Both convergence layers support feature-flag rollback:

  • setCCREnabled(false) — Disables CCR routing, falls back to individual module implementations
  • setCCLEnabled(false) — Disables CCL routing, falls back to individual infrastructure modules

Rollback is immediate and requires no reboot.
